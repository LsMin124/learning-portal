# JPA 4강: 연관관계 매핑 — 치트시트

> 객체의 양방향 ↔ DB 의 한 방향(FK) 비대칭을 *주인* 으로 흡수. N+1·cascade·`@ManyToMany` 함정 모음.
> **TL;DR** → **Quick Reference** → **Mind Map** 3 섹션.

---

# 1. TL;DR (5분 요약)

## 핵심 6줄

1. **객체는 양방향, DB 는 한 방향 (FK)**. JPA 가 이 비대칭을 *연관관계 주인* 으로 흡수. **주인 = FK 가 있는 쪽 (`@ManyToOne`)**.
2. **모든 연관관계는 `fetch = FetchType.LAZY` 명시**. `@ManyToOne` 과 `@OneToOne` 디폴트가 EAGER — 함정.
3. **`@OneToMany` 단방향 X**. 항상 `@ManyToOne` 부터 시작. 양방향이 *진짜 필요* 할 때만 `@OneToMany(mappedBy)` 추가.
4. **N+1 해결책 4 가지**: JOIN FETCH / `@EntityGraph` / `@BatchSize` / DTO Projection.
5. **JOIN FETCH + `OneToMany` + 페이징 동시 사용 금지** — 메모리 페이징 fallback → OOM. DTO Projection 또는 `@BatchSize`.
6. **`@ManyToMany` 직접 사용 X**. 항상 *중간 엔티티* + `@ManyToOne` 두 개로 풀기. 추가 컬럼·확장성 ↑.

## 가장 중요한 코드 3개

```java
// (1) 가장 흔한 @ManyToOne 단방향 - 반드시 LAZY
@Entity
public class Reply {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String content;

    @ManyToOne(fetch = FetchType.LAZY)           // 필수 명시
    @JoinColumn(name = "board_id", nullable = false)
    private Board board;
}
```

```java
// (2) 양방향 + cascade + orphanRemoval + 편의 메서드
@Entity
public class Board {
    @OneToMany(mappedBy = "board",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Reply> replies = new ArrayList<>();

    public void addReply(Reply r) {
        replies.add(r);
        r.setBoard(this);    // 양쪽 동시 세팅
    }
}
```

```java
// (3) N+1 회피 - JOIN FETCH (단건) 또는 DTO (페이징)
@Query("SELECT DISTINCT b FROM Board b LEFT JOIN FETCH b.replies WHERE b.id = :id")
Optional<Board> findByIdWithReplies(@Param("id") Long id);

// 페이징 + 컬렉션 = DTO Projection 필수
@Query("SELECT new com.example.dto.BoardSummary(b.id, b.title) FROM Board b")
Page<BoardSummary> findSummaries(Pageable p);
```

## 면접 한 줄 답변

- **Q. 연관관계의 주인을 정하는 기준은?** → **FK 컬럼이 있는 쪽이 주인**. 보통 `@ManyToOne` 쪽. 반대편은 `mappedBy` 로 *주인 아님* 선언.
- **Q. N+1 문제는 어떻게 해결하나요?** → **LAZY 기본** + 상황별 ① JOIN FETCH (단건) ② `@EntityGraph` (재사용) ③ `@BatchSize` (페이징 호환) ④ DTO Projection (대규모).
- **Q. JOIN FETCH + 페이징은 왜 위험한가요?** → `OneToMany` 의 JOIN 은 *row 부풀림*. DB `LIMIT/OFFSET` 으로 row 단위 자르면 부모 데이터 불완전 → Hibernate 가 **메모리 페이징 fallback** → OOM.
- **Q. `@ManyToMany` 를 안 쓰는 이유는?** → **중간 테이블에 추가 컬럼 못 넣음** + **발행 SQL 추적 어려움** + **확장성 0**. 항상 중간 엔티티 패턴.

# 2. Quick Reference (실무 복붙)

## 2.1 4 종 연관관계 어노테이션

| 어노테이션 | 사용처 | 디폴트 fetch | 권장 |
|--|--|--|--|
| `@ManyToOne` | 가장 흔함 (자식 → 부모) | **EAGER** ❗ | `fetch = LAZY` 필수 |
| `@OneToMany` | 양방향 시 부모 → 자식 | LAZY | `mappedBy` 필수 |
| `@OneToOne` | 1:1 (Member ↔ Profile) | **EAGER** ❗ | `fetch = LAZY` 필수, 단방향 권장 |
| `@ManyToMany` | N:M | LAZY | **안 씀**. 중간 엔티티로 풀기 |

## 2.2 mappedBy 사용 패턴

```java
// 단방향 - mappedBy 없음 (FK 만 있음)
@ManyToOne @JoinColumn(name="board_id") private Board board;

// 양방향 - 주인 (mappedBy 없음)
@ManyToOne @JoinColumn(name="board_id") private Board board;

// 양방향 - 거울 (mappedBy 있음)
@OneToMany(mappedBy = "board") private List<Reply> replies;
```

> 한 연관관계에 `mappedBy` 와 `@JoinColumn` 을 *같은 쪽에 동시* 사용 X.

## 2.3 fetch 전략

```java
@ManyToOne(fetch = FetchType.LAZY)   // 권장 - 명시
@OneToOne(fetch = FetchType.LAZY)    // 권장 - 명시
@OneToMany   // LAZY 가 디폴트지만 명시 권장
@ManyToMany  // LAZY 가 디폴트
```

**EAGER 금지 원칙**: 의도치 않은 JOIN, 추적 어려움, N+1 숨김. *명시적 즉시 로딩* 이 필요하면 `JOIN FETCH` 또는 `@EntityGraph`.

## 2.4 N+1 해결책

| 방법 | 코드 | 페이징 호환 | 적합 상황 |
|--|--|--|--|
| JOIN FETCH | `SELECT b FROM Board b JOIN FETCH b.replies` | **OneToMany 시 X** | 단건·소량 |
| `@EntityGraph` | `@EntityGraph(attributePaths = "replies")` | OneToMany 시 X | 재사용성 |
| `@BatchSize` | `@BatchSize(size = 100)` on 컬렉션 | **O** | 페이징 + 컬렉션 |
| DTO Projection | `SELECT new pkg.DTO(...)` | **O** | 대규모·페이징 |

**전역 설정**:
```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

## 2.5 cascade & orphanRemoval

| 옵션 | 의미 |
|--|--|
| `cascade = CascadeType.PERSIST` | 부모 persist 시 자식도 |
| `cascade = CascadeType.REMOVE` | 부모 remove 시 자식도 |
| `cascade = CascadeType.ALL` | 모든 작업 전파 |
| `orphanRemoval = true` | 컬렉션에서 자식 제거 시 DELETE |

**사용 조건**: 자식이 부모에 **독점적으로** 묶일 때만. 공유 자식 (Tag 등) 에는 위험.

## 2.6 @ManyToMany 풀기 패턴

```java
// 비추 - @ManyToMany 직접
@ManyToMany
@JoinTable(name = "student_course")
private List<Course> courses;

// 권장 - 중간 엔티티
@Entity
public class Enrollment {
    @Id @GeneratedValue Long id;
    @ManyToOne(fetch = LAZY) @JoinColumn(name = "student_id") Student student;
    @ManyToOne(fetch = LAZY) @JoinColumn(name = "course_id") Course course;
    LocalDateTime enrolledAt;
    Integer score;   // 추가 컬럼 자유
}
```

## 2.7 자주 빠지는 함정 모음 (4강)

| 함정 | 정정 |
|--|--|
| `@ManyToOne`, `@OneToOne` 디폴트 EAGER | **항상 LAZY 명시** |
| `@OneToMany` 만 단방향 (mappedBy 없이) | 별도 UPDATE 쿼리. `@ManyToOne` 을 주인으로 |
| mappedBy 와 `@JoinColumn` 동시 사용 | 둘 중 하나만 |
| N+1 을 EAGER 로 해결 시도 | EAGER 가 *N+1 을 숨김*. LAZY + JOIN FETCH/EntityGraph/BatchSize |
| JOIN FETCH + OneToMany + 페이징 | OOM. DTO Projection 또는 BatchSize |
| JOIN FETCH 결과 row 부풀림 | `DISTINCT` 또는 `Set<T>` |
| `@ManyToMany` 직접 | 중간 엔티티 패턴 |
| 한쪽만 set (편의 메서드 없음) | 객체 그래프 불일치. add/remove 편의 메서드 |
| cascade=ALL + orphanRemoval 을 공유 자식에 | 데이터 무결성 깨짐. 독점 자식에만 |
| `@OneToOne` 반대편 LAZY 안 됨 | Hibernate 한계. 단방향만 쓰거나 `@MapsId` |
| 양방향 + Lombok `@ToString` | 무한 순회 SO. `@ToString.Exclude` |
| List<T> 의 순서 보장 기대 | 보장 X. `@OrderBy` 또는 `@OrderColumn` |

## 2.8 약어 표

| 약어 | 풀어쓰기 |
|--|--|
| FK | Foreign Key |
| LAZY / EAGER | 지연 / 즉시 로딩 |
| OOM | OutOfMemoryError |
| LIE | LazyInitializationException |
| DDD | Domain-Driven Design |
| Aggregate Root | DDD 의 자식 소유 부모 |

## 3.2 4강 학습 진도 체크리스트

### 기본 원리
- [ ] 객체와 RDB 의 연관관계 표현 차이 (양방향 vs 한 방향 FK) 안다
- [ ] 연관관계의 주인 정의·정하는 규칙 외움
- [ ] `mappedBy` 와 `@JoinColumn` 의 차이 안다
- [ ] 양쪽 주인 (mappedBy 빠뜨림) 의 결과 (별도 중간 테이블) 안다

### @ManyToOne
- [ ] 가장 흔한 단방향 N:1 매핑 작성 가능
- [ ] `@JoinColumn(name=..., nullable=false)` 의 역할 안다
- [ ] **fetch = FetchType.LAZY 명시 필수** 임을 안다 (디폴트 EAGER 함정)

### @OneToMany 양방향
- [ ] `mappedBy` 명시 패턴 안다
- [ ] 컬렉션 `new ArrayList<>()` 초기화 안다
- [ ] 단방향만으로 충분한지 *먼저 자문* 하는 습관

### fetch 전략
- [ ] 4 어노테이션 디폴트 fetch 외움
- [ ] @ManyToOne / @OneToOne 의 디폴트 EAGER 가 함정인 이유 안다
- [ ] LAZY 의 동적 프록시 매커니즘 안다
- [ ] EAGER 의 3 가지 위험 (불필요 JOIN, N+1, 페이징 fallback) 안다

### N+1 문제 (★)
- [ ] 발생 조건과 결과 (1+N 쿼리) 안다
- [ ] EAGER 가 N+1 을 *숨긴다* 는 점 안다
- [ ] 4 가지 해결책 (JOIN FETCH / EntityGraph / BatchSize / DTO Projection) 외움
- [ ] 각 해결책의 적합 상황 안다 (페이징 호환 여부)

### JOIN FETCH 함정
- [ ] **JOIN FETCH + OneToMany + 페이징 = OOM** 위험 알고 회피
- [ ] JOIN FETCH 결과의 row 부풀림 → DISTINCT 또는 Set 사용
- [ ] @ManyToOne, @OneToOne JOIN FETCH 는 페이징 OK 인 것 안다

### cascade & orphanRemoval
- [ ] 6 가지 CascadeType 의 의미 안다
- [ ] orphanRemoval 과 cascade=REMOVE 의 차이 안다
- [ ] 공유 자식에 cascade=ALL/orphanRemoval=true 적용 X
- [ ] DDD Aggregate Root 와의 관계 안다

### @ManyToMany
- [ ] 직접 사용을 피하는 이유 3 가지 (추가 컬럼 / 추적 / 확장성) 안다
- [ ] 중간 엔티티 + @ManyToOne 두 개 패턴 작성 가능

### 양방향 편의 메서드
- [ ] addX / removeX 패턴 작성 가능
- [ ] 한쪽만 set 시 발생하는 객체 그래프 불일치 안다

## 3.4 4강 자기 점검 신호

- "이 객체에 컬렉션이 진짜 필요한가?" 가 자연스럽게 떠오르면 → 통과
- "fetch 디폴트가 뭐였지?" 가 헷갈리면 → Part E 재학습
- "N+1 인가?" 가 *코드 보자마자* 떠오르면 → 면접 통과 시그널
- "이거 페이징하는데 JOIN FETCH 같이 써도 되나?" 가 헷갈리면 → Part F 의 함정 표 복습
- "이 자식이 공유되는가?" 가 cascade 부착 전에 자연스럽게 떠오르면 → 운영 사고 회피 시그널
- "@ManyToMany 쓰자" 가 떠오르면 → **중간 엔티티 패턴** 재학습
