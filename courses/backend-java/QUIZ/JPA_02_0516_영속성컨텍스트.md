### Q1. (개념) 영속성 컨텍스트가 무엇이며, Spring 환경에서 *언제* 만들어지고 *언제* 닫히는지 한 문장씩.

<details><summary>정답</summary>

**영속성 컨텍스트** = EntityManager 가 관리하는 *엔티티 보관소*. 안에 1차 캐시, 스냅샷, 쓰기 지연 SQL 저장소를 가짐.

**수명** (Spring 기본):
- 트랜잭션 시작 시점에 생성
- 트랜잭션 종료 시점에 닫힘
- 단, **OSIV 가 켜져 있으면 HTTP 응답까지 지연 닫힘** (Spring Boot 기본 OSIV=true)

</details>

### Q2. (개념) 영속성 컨텍스트 *내부의* 세 가지 데이터 구조를 들고 각각의 용도를 한 줄.

<details><summary>정답</summary>

1. **1차 캐시** (`Map<PK, Entity>`) — 영속 상태 엔티티 보관. 같은 PK 재조회 시 DB 안 가고 캐시 HIT.
2. **스냅샷** — 영속 시점의 엔티티 *원본 복사본*. Dirty Checking (변경 감지) 비교용.
3. **쓰기 지연 SQL 저장소** — flush 전까지 모아둔 INSERT/UPDATE/DELETE SQL. 트랜잭션 commit 시 배치 발송.

</details>

### Q3. (개념) 엔티티의 4 가지 상태를 나열하고 각각의 *trigger* (어떻게 그 상태로 들어가나) 를 적으시오.

<details><summary>정답</summary>

| 상태 | 정의 | trigger |
|--|--|--|
| **transient (비영속)** | JPA 가 모름 | `new Board()` 직후 |
| **managed (영속)** | 영속성 컨텍스트 등록 | `em.persist(b)`, `em.find(...)`, JPQL 결과 |
| **detached (준영속)** | 컨텍스트에서 분리 | `em.detach(b)`, `em.close()`, `em.clear()`, 트랜잭션 종료 |
| **removed (삭제 예정)** | 다음 flush 에 DELETE | `em.remove(b)` |

managed → detached → managed 재진입은 `em.merge(b)`.

</details>

### Q4. (적용) 다음 코드의 *각 줄에서* b 의 상태를 적으시오.
```java
@Transactional
public void check() {
    Board b = new Board();         // (1)
    b.setTitle("hi");
    em.persist(b);                  // (2)
    em.detach(b);                   // (3)
    Board merged = em.merge(b);     // (4) — merged 의 상태
    em.remove(merged);              // (5) — merged 의 상태
}
```

<details><summary>정답</summary>

| 줄 | b (또는 merged) 의 상태 |
|--|--|
| (1) `new Board()` | **transient** |
| (2) `em.persist(b)` | **managed** (영속) — 영속성 컨텍스트 등록, INSERT 예약 |
| (3) `em.detach(b)` | **detached** (준영속) — JPA 가 더는 추적 안 함 |
| (4) `em.merge(b)` | **merged 는 managed**. b 는 *여전히 detached*. |
| (5) `em.remove(merged)` | merged 는 **removed** — 다음 flush 에 DELETE |

핵심: `merge` 가 *b 를 살리는 게 아니라*, 새 복사본 (merged) 을 영속화하고 반환.

</details>

### Q5. (적용) 다음 메서드가 정상 실행 후 DB 의 board 테이블에 발생하는 변화는?
```java
@Transactional
public void changeTitle(Long id, String newTitle) {
    Board b = boardRepo.findById(id).orElseThrow();
    b.setTitle(newTitle);
    // 끝. save() 호출 X
}
```

<details><summary>정답</summary>

**UPDATE board SET title=? WHERE id=?** 발생 (변경된 컬럼만, 기본은 전체 컬럼 SET).

이유: **Dirty Checking (변경 감지)**.

3 조건 모두 만족:
- ① 엔티티가 **managed** (`findById` 결과)
- ② **트랜잭션 안** (`@Transactional`)
- ③ 트랜잭션 **commit** 시점 도달

영속성 컨텍스트가 *스냅샷 vs 현재* 비교 → 변경된 필드만 UPDATE SQL 자동 생성 → flush 시 DB 발송.

`save(b)` 안 해도 됨 — 호출해도 같은 결과 (이중 호출 무의미).

</details>

### Q6. (적용) `@Transactional(readOnly = true)` 가 영속성 컨텍스트 동작에 미치는 영향 두 가지를 적으시오.

<details><summary>정답</summary>

1. **스냅샷 생성 안 함** — Dirty Checking 자체가 꺼짐. setter 호출해도 UPDATE 발생 X. 메모리 절약.
2. **flush mode 변경** — `MANUAL` 또는 `COMMIT` 으로 — JPQL 실행 직전의 *불필요한 flush* 도 생략.

성능: SELECT 만 하는 메서드는 readOnly=true 가 정석.

함의: readOnly=true 안에서 setter 로 수정해도 변경이 *안 됨* (또는 일부 구현체에서 예외). 의도가 수정이면 readOnly 빼야.

</details>

### Q7. (적용) 다음 두 코드의 결과 차이를 설명하시오.
```java
// 코드 A
@Transactional
public Board read1(Long id) {
    Board b1 = em.find(Board.class, id);
    Board b2 = em.find(Board.class, id);
    return b1;     // b1 == b2 ?
}

// 코드 B
public Board read2(Long id) {
    Board b1 = em.find(Board.class, id);    // 트랜잭션 시작·종료
    Board b2 = em.find(Board.class, id);    // 또 트랜잭션 시작·종료
    return b1;     // b1 == b2 ?
}
```
(코드 B 는 @Transactional 없음 — 메서드마다 새 트랜잭션이라고 가정)

<details><summary>정답</summary>

**코드 A**: `b1 == b2` **true**. 같은 트랜잭션 → 같은 영속성 컨텍스트 → 같은 PK 는 1차 캐시 HIT → 동일 객체.

**코드 B**: `b1 == b2` **false**. 각 호출이 별도 트랜잭션 → 별도 영속성 컨텍스트 → 1차 캐시 공유 X → 다른 메모리의 객체.

핵심: **동일성 보장은 *같은 영속성 컨텍스트 안* 에서만**. 트랜잭션 경계를 넘으면 다른 객체.

</details>

### Q8. (디버그) 다음 코드가 *UPDATE 안 되는* 이유를 진단하시오.
```java
// @Transactional 없음
public void changeTitle(Long id, String newTitle) {
    Board b = boardRepo.findById(id).orElseThrow();
    b.setTitle(newTitle);
}
```

<details><summary>정답</summary>

**원인**: `@Transactional` 이 없으면 트랜잭션 경계 안에 들어가지 않음. 

- `findById()` 자체는 Spring Data JPA 가 *짧은 트랜잭션* 으로 감싸 실행되지만, **그 트랜잭션이 메서드 진입 시점에 이미 끝남**.
- 반환된 b 는 **detached 상태**.
- `b.setTitle(...)` 은 자바 객체만 변경. JPA 가 더는 추적 안 함.
- 메서드 끝나도 어떤 트랜잭션도 commit 시점에 도달하지 않으므로 UPDATE 발행 X.

**수정**:
```java
@Transactional  // 추가
public void changeTitle(Long id, String newTitle) { ... }
```

</details>

### Q9. (디버그) 다음 코드의 문제를 지적하시오.
```java
@Transactional
public Board updateBoard(Long id, String newTitle) {
    Board b = em.find(Board.class, id);
    em.detach(b);                 // (?)
    b.setTitle(newTitle);
    return b;
}
```

<details><summary>정답</summary>

`em.detach(b)` 직후 b 는 **detached 상태**. JPA 가 더는 추적 안 함. `b.setTitle(...)` 은 자바 객체만 변경, UPDATE 발생 X.

의도가 *수정* 이라면 detach 호출 자체가 *잘못*. 삭제하면 됨:

```java
@Transactional
public Board updateBoard(Long id, String newTitle) {
    Board b = em.find(Board.class, id);    // managed
    b.setTitle(newTitle);                   // dirty checking 대상
    return b;
}
```

만약 *의도적으로 detached* 로 만든 뒤 다시 영속화하려면:

```java
em.detach(b);
b.setTitle(newTitle);
Board merged = em.merge(b);   // merged 가 managed, b 는 여전히 detached
return merged;                 // 반환은 merged 로!
```

</details>

### Q10. (디버그) 다음 코드의 함정을 지적하고 수정하시오.
```java
@Transactional
public void updateFromDetached(Board detachedBoard) {
    em.merge(detachedBoard);                    // (?)
    detachedBoard.setTitle("title from outside");
}
```

<details><summary>정답</summary>

**함정**: `em.merge(b)` 는 *b 자체를 영속화* 하는 게 아니라, **새 복사본을 영속화하고 반환**. detachedBoard 는 *여전히 detached*.

그래서 `detachedBoard.setTitle(...)` 은 detached 객체 수정 → UPDATE 안 됨.

**수정**:

```java
@Transactional
public void updateFromDetached(Board detachedBoard) {
    Board managed = em.merge(detachedBoard);   // 반환값을 받음
    managed.setTitle("title from outside");     // managed 의 setter → dirty checking
    // 또는 한 줄: em.merge(detachedBoard).setTitle("...");
}
```

**원칙**: `merge` 의 반환값을 *반드시* 받아서 그 객체로 작업.

</details>

### Q11. (디버그) 다음 코드의 트랜잭션이 적용되지 않는 이유는?
```java
@Service
public class BoardService {

    public void outer(Long id) {
        this.inner(id);   // same-class 호출
    }

    @Transactional
    public void inner(Long id) {
        Board b = boardRepo.findById(id).orElseThrow();
        b.setTitle("new");
    }
}
```

<details><summary>정답</summary>

**원인**: Spring 의 `@Transactional` 은 **AOP 프록시** 로 동작. 외부 호출자가 *프록시* 를 거쳐 메서드 호출할 때만 트랜잭션 적용.

`this.inner(id)` 는 같은 클래스 안의 직접 호출 → **프록시 우회** → 트랜잭션 적용 안 됨 → `inner` 의 dirty checking 도 동작 안 함 → UPDATE 발생 X.

**수정 방법**:

1) 메서드 분리 (가장 흔함):
```java
@Service @RequiredArgsConstructor
public class BoardService {
    private final BoardInnerService innerService;
    public void outer(Long id) { innerService.inner(id); }
}

@Service
public class BoardInnerService {
    @Transactional
    public void inner(Long id) { ... }
}
```

2) Self-injection (덜 권장):
```java
@Service
public class BoardService {
    @Autowired @Lazy private BoardService self;
    public void outer(Long id) { self.inner(id); }
    @Transactional public void inner(Long id) { ... }
}
```

3) outer 자체에 `@Transactional` 부착 (가장 단순한 경우).

</details>

### Q12. (디버그) Controller 에서 JSON 직렬화 중 `LazyInitializationException` 가 발생. OSIV 설정과 관련해 원인과 해결책 둘을 적으시오.

<details><summary>정답</summary>

**원인**: `open-in-view: false` 인 환경에서, Service `@Transactional` 메서드가 끝남 → EntityManager 닫힘 → 반환된 엔티티의 LAZY 컬렉션 (예: `board.getReplies()`) 에 *Controller·JSON 직렬화 시점* 에 접근 시도 → 이미 닫힌 컨텍스트라 *프록시가 초기화 못 함* → 예외.

**해결책**:

1) **DTO 변환 패턴** (권장): Entity 가 트랜잭션 밖으로 안 나가게.
```java
@Transactional(readOnly = true)
public BoardDto getBoard(Long id) {
    Board b = boardRepo.findById(id).orElseThrow();
    return new BoardDto(b);  // 트랜잭션 안에서 LAZY 다 풀어 DTO 로 변환
}
```

2) **JOIN FETCH 로 즉시 로딩** (4 강에서 다룸):
```java
@Query("SELECT b FROM Board b LEFT JOIN FETCH b.replies WHERE b.id = :id")
Optional<Board> findByIdWithReplies(@Param("id") Long id);
```

3) (임시 대처) `open-in-view: true` 로 두기 — 부하 시 커넥션 풀 점유 문제. 권장 X.

</details>

### Q13. (면접) "JPA 의 변경 감지 (Dirty Checking) 가 동작하는 원리와 조건" 을 1분 내로 설명.

<details><summary>정답</summary>

**원리**:
- 영속화 시점에 영속성 컨텍스트가 엔티티의 *최초 스냅샷* 을 저장
- 트랜잭션 commit 시점에 *현재 엔티티* 와 *스냅샷* 을 필드별 비교
- 변경된 필드가 있으면 UPDATE SQL 자동 생성·flush

**조건 3 가지**:
1. 엔티티가 **managed** 상태
2. **트랜잭션 안**
3. 트랜잭션 **commit (또는 flush)** 도달

**MyBatis 와의 차이**: MyBatis 는 *명시적 UPDATE SQL* 작성. JPA 는 *자바 객체 수정* 만으로 자동. *학습 곡선은 가파르지만* 코드가 도메인 중심으로 깔끔해짐.

**함의**: `@Transactional` 없는 환경 (Controller 의 응답 변환 등) 에서는 setter 호출이 의미 없음. 트랜잭션 경계를 *항상* 의식해야.

</details>

### Q14. (면접) Spring Boot 의 `spring.jpa.open-in-view` 옵션. *true/false* 의 trade-off 를 답하시오.

<details><summary>정답</summary>

**OSIV (Open Session In View)** = 영속성 컨텍스트의 수명을 *HTTP 응답까지* 늘리는 패턴.

| | `true` (Spring Boot 기본) | `false` |
|--|--|--|
| 영속성 컨텍스트 수명 | HTTP 응답까지 | 트랜잭션 종료까지 |
| Controller·View 에서 LAZY | 동작 (편함) | `LazyInitializationException` |
| DB 커넥션 점유 시간 | 길다 (HTTP 응답까지) | 짧다 (트랜잭션 안에서만) |
| 부하 시 커넥션 풀 | **고갈 위험** | 안전 |

**실무 가이드**: 학습·MVP 는 true. 운영 부하 큰 서비스는 false + **DTO 변환 패턴**. 마이크로서비스·API 서버는 보통 false.

**전환 함정**: true → false 전환 시 *기존에 동작하던 LAZY 접근 코드가 죄다 깨짐*. 점진적 변경 + 통합테스트 + 모니터링 필요.

</details>
