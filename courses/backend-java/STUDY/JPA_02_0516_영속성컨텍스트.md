# JPA 2강: 영속성 컨텍스트 (Persistence Context)

> **이 강의는 무엇인가**: JPA 의 *정체성*. 객체와 DB 를 연결하는 *중간 보관소* 인 영속성 컨텍스트, 그 안의 엔티티 4 상태, 1차 캐시, **Dirty Checking** (변경 감지), flush 의 미묘함, Spring 의 OSIV 까지.
> **왜 배우는가**: JPA 의 거의 모든 *마법* (save 없이 UPDATE 됨, 같은 PK 면 == 같은 객체, LAZY 가 갑자기 안 됨) 의 원인은 영속성 컨텍스트. 이 개념을 모르면 JPA 의 동작은 마술쇼로만 보인다. 면접·실무 모두 단골.

---

## 들어가기 전에

- **선수**: 1 강 (개념 + Entity 매핑). 트랜잭션 기초 (commit/rollback).
- **마인드셋**: "JPA 가 영리한 게 아니라, 영속성 컨텍스트라는 *작업 메모리* 가 영리한 것." 모든 함정은 이 메모리의 *수명*·*동기화 시점* 에서 발생.
- **1강 복습**: `@Entity` 클래스 = JPA 의 관리 대상. 기본 생성자 + non-final. PK 는 `Long`. enum 은 `STRING`.

---

# Part A. 영속성 컨텍스트란?

## 1. EntityManager 안의 작업 메모리

```
   Application
        |
        v
   +-----------------------------------+
   |     EntityManager (em)            |
   |  +---------------------------+    |
   |  |  Persistence Context       |   |  <- 1차 캐시
   |  |  (Map<PK, Entity>)         |   |     + 스냅샷 + 쓰기 지연 SQL 저장소
   |  +---------------------------+    |
   +-----------------------------------+
        |
        v
       DB
```

**영속성 컨텍스트** = EntityManager 가 관리하는 *엔티티 보관소*. 트랜잭션 안에서만 살아있고 끝나면 사라짐. 내부 구조는 대략:

- **1차 캐시** (`Map<PK, Entity>`) — 영속 상태 엔티티 보관
- **스냅샷** — 영속 시점의 엔티티 *원본 복사본* (Dirty Checking 비교용)
- **쓰기 지연 SQL 저장소** — flush 전까지 INSERT/UPDATE/DELETE SQL 을 모아둠

Spring 환경에서는 *대부분* 트랜잭션이 시작될 때 영속성 컨텍스트도 만들어지고, 트랜잭션 끝나면 닫힘. 그래서 **"영속성 컨텍스트의 수명 = 트랜잭션의 수명"** 이라는 단순화가 통한다 (정확히는 OSIV 설정에 따라 다름 — Part F).

## 2. 왜 이런 게 존재하나?

만약 영속성 컨텍스트가 없다면:

```java
// 영속성 컨텍스트 없는 가상 세계
Board b = boardRepo.findById(1L);
b.setTitle("changed");
// "어, 수정했네. UPDATE SQL 날려야지" — 자동으로 어떻게?
boardRepo.save(b);  // 매번 명시
```

영속성 컨텍스트가 있으면:

```java
// 실제 JPA
@Transactional
public void changeTitle(Long id, String newTitle) {
    Board b = boardRepo.findById(id);  // 영속성 컨텍스트에 등록 (managed)
    b.setTitle(newTitle);               // 자바 객체 수정
    // save() 없어도 OK — 트랜잭션 끝나면 자동 감지·UPDATE
}
```

이 차이가 *몇 줄 코드 절약* 이 아니다. 영속성 컨텍스트는 다음을 가능하게 한다:

1. **1차 캐시**: 같은 PK 는 한 번만 SELECT
2. **동일성 보장**: 같은 PK 면 `==` 같은 객체
3. **Dirty Checking**: setter 만 호출해도 UPDATE 자동
4. **쓰기 지연**: INSERT/UPDATE 를 모아 flush 시 한 번에 보냄 (성능)
5. **트랜잭션 경계의 일관성**: 같은 트랜잭션 내 같은 엔티티는 항상 같은 상태

# Part B. 엔티티 4 상태와 상태 전환

JPA 의 모든 동작은 *엔티티가 어느 상태인가* 에 달려있다.

## 1. 상태 정의

```
   new (transient, 비영속)
   -----------------------
   - new Board() 직후
   - JPA 가 모름
   - 1 차 캐시 X, dirty checking X

            |
            v   em.persist(b)

   managed (영속)
   ------------------
   - 영속성 컨텍스트에 등록됨
   - 1 차 캐시에 보관
   - dirty checking 대상
   - 다음 flush 시 INSERT/UPDATE 자동

            |
            v   em.detach(b) / em.close() / em.clear()

   detached (준영속)
   ------------------
   - 영속성 컨텍스트에서 분리됨
   - JPA 가 더는 추적 안 함
   - 다시 합치려면 em.merge(b)

            |
            v   em.remove(b) (managed 에서)

   removed (삭제 예정)
   ---------------------
   - 영속성 컨텍스트에서 제외
   - 다음 flush 시 DELETE SQL 발행
```

## 2. 코드로 보는 4 상태

```java
@Transactional
public void demonstrateStates() {
    // 1) transient
    Board b = new Board();
    b.setTitle("test");
    // JPA 모름. b 는 그냥 자바 객체.

    // 2) managed
    em.persist(b);
    // 영속성 컨텍스트에 등록. b 는 이제 영속.
    // 이 시점 b.getId() 는 (IDENTITY 면) 이미 부여됨, (SEQUENCE 면) 곧 부여.

    b.setTitle("changed");   // dirty checking 대상
    // setter 만 호출 — 트랜잭션 끝나면 UPDATE 자동.

    // 3) detached
    em.detach(b);
    b.setTitle("further");   // JPA 모름. UPDATE 안 됨.

    // 다시 영속화하려면:
    Board merged = em.merge(b);
    // 주의: b 자체가 영속 되는 게 아니라, *복사본 (merged)* 이 영속.

    // 4) removed
    em.remove(merged);
    // 영속성 컨텍스트에서 제외. 다음 flush 에 DELETE.
}
// 트랜잭션 commit → flush → DB 반영 → 영속성 컨텍스트 종료
```

> **함정 1**: `em.detach(b)` 후 `b.setTitle(...)` 은 *자바 객체* 만 바꿈. UPDATE 안 됨. 다시 살리려면 `em.merge(b)`.

> **함정 2**: `merge()` 는 *기존 b 를 영속화* 하는 게 아니라, **새 복사본을 영속화하고 반환**. 반환값을 받아 그걸 쓰는 게 안전.

## 3. Spring Data JPA 의 `save()` 의 내부

```java
// Spring Data JPA 의 save() 내부 (단순화)
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {   // PK 가 null/0 이면
        em.persist(entity);                  // INSERT 경로
        return entity;
    } else {
        return em.merge(entity);             // UPDATE 경로
    }
}
```

함의:
- *PK 가 없는* 새 엔티티 → `persist()` (INSERT)
- *PK 가 이미 있는* (detached) 엔티티 → `merge()` (UPDATE — 복사본 반환)

1 강의 *PK 는 Long (래퍼) 으로* 가 이래서 중요했다 — primitive `long` 의 0 이 *PK 가 있는 것* 으로 오인되면 merge 경로로 가서 의도 다른 동작.

# Part C. 1차 캐시와 동일성 보장

## 1. 같은 PK = 같은 객체

```java
@Transactional
public void firstLevelCache() {
    Board b1 = em.find(Board.class, 1L); // SELECT 발행 (DB)
    Board b2 = em.find(Board.class, 1L); // SELECT 안 함 (1차 캐시 HIT)

    System.out.println(b1 == b2);         // true ← 같은 메모리 주소!
}
```

같은 트랜잭션 안에서 같은 PK 로 조회하면 **동일 객체 반환**. 일반 자바의 `==` 비교가 성립.

MyBatis 와 결정적 차이:

```java
// MyBatis
Board b1 = boardMapper.findById(1L);     // SELECT
Board b2 = boardMapper.findById(1L);     // 또 SELECT
System.out.println(b1 == b2);             // false ← 별개 객체
```

## 2. `equals()` 와 `hashCode()` 작성 주의

1차 캐시 안에서는 `==` 가 통하지만, **트랜잭션 경계를 넘으면** 다른 객체. 그래서 *컬렉션 (HashSet 등) 에 엔티티를 담는 경우* `equals()`/`hashCode()` 가 필요한데, 1 강에서 본 것처럼 Lombok `@Data` 의 전체 필드 기반은 위험.

권장:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Board b)) return false;
    return id != null && id.equals(b.id);  // PK 가 부여된 후만 비교
}

@Override
public int hashCode() {
    return getClass().hashCode();  // PK 가 변해도 일관성 유지
}
```

## 3. JPQL 과 1차 캐시의 미묘한 관계

```java
@Transactional
public void quirk() {
    Board b = em.find(Board.class, 1L);   // 1차 캐시에 b 등록
    b.setTitle("memory only");             // dirty checking 대상이지만 아직 DB 미반영

    List<Board> all = em.createQuery(
        "SELECT b FROM Board b", Board.class
    ).getResultList();
    // JPQL 실행 *전* 자동 flush 발생!
    // 그래서 위 UPDATE 가 DB 로 가고, 그 후 SELECT 가 실행됨.
    // all 안의 b 는 1차 캐시의 같은 객체.

    // 다만 *1 차 캐시에 없던 다른 엔티티* 가 JPQL 로 들어오면 → DB 에서 가져와 1 차 캐시에 추가.
}
```

핵심: **JPQL 은 DB 를 SELECT** 하지만, 결과 객체는 *1 차 캐시 우선* 으로 매핑됨. 즉 같은 PK 면 DB 결과 무시하고 캐시 객체 반환.

# Part D. Dirty Checking (변경 감지) — JPA 의 마법

## 1. save() 없이 UPDATE 되는 이유

```java
@Transactional
public void changeTitle(Long id, String newTitle) {
    Board b = boardRepo.findById(id).orElseThrow();  // managed 상태
    b.setTitle(newTitle);                             // 자바 객체 변경
    // 끝. boardRepo.save(b) 호출 X
}
// 트랜잭션 commit 시점에:
//   1) 영속성 컨텍스트가 *최초 스냅샷* 과 *현재 b* 를 비교
//   2) 변경된 필드만 UPDATE SQL 생성
//   3) DB 로 flush
```

이게 **Dirty Checking (변경 감지)**.

## 2. 동작 조건 3 가지

Dirty checking 이 동작하려면 *모두* 만족:

1. **엔티티가 managed 상태**
2. **트랜잭션 안**
3. **트랜잭션 commit (또는 flush) 도달**

하나라도 빠지면 동작 안 함:

- `em.detach()` 한 엔티티의 setter 호출 → UPDATE 안 됨 (조건 1 위반)
- `@Transactional` 없는 메서드에서 setter 호출 → managed 자체가 안 됨 (조건 2 위반)
- 예외 던지고 트랜잭션 롤백 → UPDATE 안 됨 (조건 3 위반, 의도된 동작)

## 3. 스냅샷의 원리

```
   영속화 시점:
   +----------------------+      +----------------------+
   |  Board (id=1)        |      | snapshot copy        |
   |  title = "old"       | ---> | title = "old"        |
   |  viewCnt = 0         |      | viewCnt = 0          |
   +----------------------+      +----------------------+

   수정 후:
   +----------------------+      +----------------------+
   |  Board (id=1)        |      | snapshot             |
   |  title = "new"       |  vs  | title = "old"        |
   |  viewCnt = 0         |      | viewCnt = 0          |
   +----------------------+      +----------------------+

   commit 시 비교 -> title 만 변경됨 -> UPDATE board SET title='new' WHERE id=1
```

스냅샷은 영속성 컨텍스트가 *내부적으로* 가진 복사본. `@Transactional(readOnly = true)` 면 스냅샷 자체를 안 만들어 메모리·성능 절약.

## 4. *변경된 필드만* UPDATE? — `@DynamicUpdate`

기본 동작 (Hibernate) 은 *모든 필드를 SET 절에 넣는* UPDATE:

```sql
UPDATE board
SET title = ?, content = ?, writer = ?, reg_date = ?, view_cnt = ?
WHERE id = ?
```

이게 더 효율적인 경우가 많다 (PreparedStatement 캐싱). 정말 *변경된 컬럼만* SET 하고 싶으면:

```java
@Entity
@DynamicUpdate
public class Board { ... }
```

다만 대부분 기본 전체 UPDATE 가 충분.

# Part E. Flush — DB 로 보내는 시점

## 1. flush 의 정의

**flush** = 영속성 컨텍스트의 변경분 (쓰기 지연 SQL 저장소의 INSERT/UPDATE/DELETE) 을 *DB 로 보내는* 동작.

`flush ≠ commit`:
- flush 는 *SQL 을 DB 로* 보낼 뿐. 트랜잭션은 진행 중.
- commit 은 *트랜잭션 종료* (그 직전 자동 flush 도 발생).
- flush 했다고 다른 트랜잭션에서 보이는 건 격리 수준에 따라.

## 2. 자동 flush 시점 3 가지

```
1. 트랜잭션 commit 직전     (가장 흔함)
2. JPQL 쿼리 실행 직전       (정합성 보장 위해)
3. 명시적 em.flush() 호출    (드물게 필요)
```

> **함정 — JPQL flush**: `em.persist(b)` 후 곧바로 JPQL `SELECT b FROM Board b ...` 를 실행하면, JPQL 실행 *직전* 자동 flush 가 발생해 b 가 DB 에 들어가고 SELECT 결과에 잡힌다. 이게 없으면 JPQL 이 DB 에 없는 b 를 못 봤겠지.

> **반대 함정 — `IDENTITY` 전략**: 1 강에서 본 PK 전략 중 IDENTITY 는 *persist 시점에 즉시 INSERT* 됨 (PK 받으려고). 다른 전략 (SEQUENCE) 은 *쓰기 지연* 으로 트랜잭션 commit 까지 INSERT 가 미뤄질 수 있어 성능 ↑.

## 3. 쓰기 지연 (Write-behind)

```java
@Transactional
public void writeMultiple() {
    em.persist(b1);   // INSERT SQL 생성·저장 (아직 DB 안 감)
    em.persist(b2);   // 또 저장
    em.persist(b3);   // 또 저장
    // 트랜잭션 commit → flush → INSERT 3 개를 한 번에 보냄 (배치)
}
```

JDBC 의 batch insert 와 결합하면 SQL 라운드트립 횟수 ↓ → 성능 ↑.

옵션: `application.yml` 에서 `hibernate.jdbc.batch_size: 50` 설정 시 50 개씩 묶어 보냄.

> **IDENTITY 전략은 쓰기 지연 불가**. PK 받으려고 즉시 INSERT. MySQL 쓰는 한 어쩔 수 없는 trade-off.

## 4. flush mode

```java
em.setFlushMode(FlushModeType.AUTO);    // 기본. JPQL 실행 직전 + commit 직전
em.setFlushMode(FlushModeType.COMMIT);  // commit 직전만. JPQL 실행 전에 flush 안 함 → 데이터 안 보일 수 있음
```

대부분 AUTO 가 안전. COMMIT 은 정합성 깨질 위험이 있어 특수 케이스 외 비추.

# Part F. Spring 의 OSIV (Open Session In View)

영속성 컨텍스트의 수명을 *어디까지* 늘릴지의 문제.

## 1. OSIV 가 켜져 있을 때 (Spring Boot 기본)

```
[HTTP Request]
       |
       v
+--------------------------+
|  Filter / Interceptor    |  <- 여기서 EntityManager 만들어짐
+--------------------------+
       |
       v
+--------------------------+
|  Controller              |
+--------------------------+
       |
       v
+--------------------------+
|  Service @Transactional  |  <- 트랜잭션 시작·종료
+--------------------------+
       |
       v
+--------------------------+
|  Repository              |
+--------------------------+
       |
       v
+--------------------------+
|  View 렌더링 (JSON 등)    |  <- 영속성 컨텍스트 *여전히 살아있음*
+--------------------------+
       |
       v
[HTTP Response]              <- 여기서 EntityManager 닫힘
```

- **장점**: Controller·View 에서도 LAZY 로딩 가능 (`b.getReplies()` 가 동작).
- **단점**: 영속성 컨텍스트가 *HTTP 응답까지* 오래 살아있어 *DB 커넥션* 도 그동안 점유.

## 2. OSIV 가 꺼져 있을 때

```
@Transactional 끝 → EntityManager 닫힘 → 그 이후 LAZY 접근 시도하면:
   LazyInitializationException
```

해결책:
- Service 안에서 *필요한 모든 LAZY 를 미리 초기화*
- DTO 로 변환해서 Controller 로 넘김 (Entity 가 아예 트랜잭션 밖으로 안 나감)
- `JOIN FETCH` 로 즉시 로딩 (4 강에서 다룸)

## 3. application.yml 설정

```yaml
spring:
  jpa:
    open-in-view: true   # 기본 (Spring Boot)
    # open-in-view: false   # 끄려면
```

## 4. 실무 가이드

| 상황 | 추천 |
|--|--|
| 학습·MVP | `open-in-view: true` (편함) |
| 성능 중요한 서비스 | `open-in-view: false` + DTO 변환 패턴 |
| 마이크로서비스·API 서버 | 보통 false. 그래도 어떤 DTO 패턴이 좋은지 별도 학습 필요. |

> **함정**: OSIV 가 켜진 상태로 운영하다가 *부하 늘면* DB 커넥션 풀 고갈 → 응답 지연. 모니터링 + 점진 전환이 안전.

## 자주 빠지는 함정

| 함정 | 해결 |
|--|--|
| `@Transactional` 없는 메서드에서 setter 호출 → UPDATE 안 됨 | 트랜잭션 안에서만 dirty checking 동작. `@Transactional` 추가 |
| `em.detach()` 후 setter 호출 → UPDATE 안 됨 | detached 는 추적 안 됨. `em.merge()` 로 다시 합치거나 `em.find()` 후 수정 |
| `merge(b)` 가 b 자체를 영속화한다고 오해 | merge 는 *복사본을 영속화하고 반환*. 반환값을 써야 함 |
| `@Transactional` 같은 클래스 내부 호출 → 트랜잭션 적용 안 됨 | Spring AOP 프록시 우회. 메서드 분리 또는 self-injection |
| `@Transactional(readOnly = true)` 인데 setter 호출 → 변경 안 됨 (또는 예외) | readOnly 는 dirty checking 끔. 수정 의도라면 readOnly 빼기 |
| LAZY 컬렉션을 Controller/View 에서 접근 → `LazyInitializationException` | OSIV 켜기 또는 Service 안에서 미리 초기화 / DTO 변환 |
| primitive `long` PK 로 `save()` 호출 → 의도와 다른 merge 경로 | `Long` 으로 (1 강) |
| `em.find()` 와 JPQL 의 결과가 *같지 않을 것* 같지만 1차 캐시로 같은 객체 | 의도된 동작. 동일성 보장. |
| `IDENTITY` 전략 쓰는데 *쓰기 지연이 안 됨* 이라고 함 | IDENTITY 는 persist 시 즉시 INSERT 가 필수. 어쩔 수 없음. 배치 성능 필요하면 SEQUENCE 고려 (DB 가 지원해야) |
| `save()` 후 또 setter 로 수정 → UPDATE 두 번 발생할까? | 보통 한 번. 1차 캐시의 같은 row 라 영속성 컨텍스트가 변경분만 모아 한 번에 UPDATE |
| 트랜잭션 안에서 같은 PK 두 번 조회 → DB 쿼리 두 번? | 한 번. 두 번째는 1차 캐시 HIT |

## 자가점검

1. 영속성 컨텍스트가 *언제* 만들어지고 *언제* 사라지는가? (Spring 환경 기준)
2. 영속성 컨텍스트가 안에 가지고 있는 *세 가지* 데이터 구조를 들어보시오.
3. 엔티티 4 상태와 각 상태의 *trigger* 를 나열하시오.
4. `em.merge()` 와 `em.persist()` 의 차이.
5. Dirty Checking 의 동작 조건 3 가지.
6. JPQL 실행 직전에 *자동 flush* 가 일어나는 이유.
7. `flush` 와 `commit` 의 차이 한 줄.
8. `@Transactional(readOnly = true)` 가 영속성 컨텍스트의 동작을 어떻게 바꾸는가?
9. OSIV 가 켜져 있을 때의 장점과 단점.
10. `merge(b)` 의 반환값을 무시하면 어떤 버그가 생길 수 있나?

<details><summary>풀이</summary>

1. **트랜잭션 시작 시점에 생성, 종료 시점에 닫힘** (Spring 의 기본). OSIV 가 켜져 있으면 HTTP 응답까지 지연 닫힘.
2. **1차 캐시** (Map<PK, Entity>), **스냅샷** (변경 감지용 원본 복사본), **쓰기 지연 SQL 저장소** (flush 전까지 모아둔 INSERT/UPDATE/DELETE).
3. **transient** (new), **managed** (`persist()` 또는 `find()` 결과), **detached** (`detach`/`close`/`clear`), **removed** (`remove()`). 상태 전환은 EntityManager API 호출이 trigger.
4. **persist**: 새 엔티티를 영속성 컨텍스트에 등록 (INSERT 예약). **merge**: detached 엔티티의 데이터를 *영속성 컨텍스트에 동기화* (복사본을 영속화, 반환). persist 는 *같은 객체* 가 영속, merge 는 *복사본* 이 영속.
5. ① 엔티티가 **managed**, ② **트랜잭션 안**, ③ 트랜잭션 **commit (또는 flush)** 도달.
6. **정합성 보장**. JPQL 은 *DB 를 SELECT* 하므로, 영속성 컨텍스트의 미반영 변경 (persist/setter) 이 DB 에 없으면 JPQL 결과가 잘못됨. 그래서 JPQL 실행 직전 자동 flush.
7. **flush** = 영속성 컨텍스트의 변경분을 DB 로 *보냄* (트랜잭션 진행 중). **commit** = 트랜잭션을 *종료* (그 직전 자동 flush 도 발생).
8. **스냅샷을 만들지 않음** → Dirty Checking 비활성화 → 메모리 절약 + 성능 ↑. flush mode 가 `MANUAL`/`COMMIT` 로 변경되어 *불필요한 flush* 도 줄임.
9. **장점**: Controller·View 에서 LAZY 로딩 가능, 코드 단순. **단점**: 영속성 컨텍스트와 DB 커넥션을 *HTTP 응답까지* 점유 → 부하 시 커넥션 풀 고갈 위험.
10. `merge()` 는 *기존 객체 (b)* 가 아니라 *복사본 (merged)* 을 영속화. `merged = em.merge(b)` 의 반환값을 무시하고 b 로 후속 작업을 하면 b 는 여전히 detached → 변경 추적 안 됨. 반환값을 받아 그걸로 작업해야.

</details>
