# 1. TL;DR (5분 요약)

## 핵심 6줄

1. **영속성 컨텍스트** = EntityManager 안의 *작업 메모리*. 내부에 **1차 캐시 / 스냅샷 / 쓰기 지연 SQL 저장소**. Spring 에서는 트랜잭션 수명 = 영속성 컨텍스트 수명.
2. 엔티티 4 상태: **transient → managed → detached / removed**. `persist/find/merge/detach/remove` 가 전환 trigger.
3. **1차 캐시 동일성 보장**: 같은 트랜잭션의 같은 PK 는 `==` 같은 객체. MyBatis 와 결정적 차이.
4. **Dirty Checking**: managed + 트랜잭션 안 + commit 도달 → setter 만 호출해도 UPDATE 자동.
5. **flush ≠ commit**. flush 는 SQL 을 DB 로 보낼 뿐. 자동 flush 시점은 *commit 직전 / JPQL 직전 / 명시적 호출*.
6. **OSIV (Spring 기본 true)**: 영속성 컨텍스트가 HTTP 응답까지 살아있어 Controller·View 에서 LAZY 가능. 단점은 DB 커넥션 점유 시간 ↑.

## 가장 중요한 코드 3개

```java
// (1) Dirty Checking - save() 없이 UPDATE
@Transactional
public void changeTitle(Long id, String newTitle) {
    Board b = boardRepo.findById(id).orElseThrow();  // managed
    b.setTitle(newTitle);                             // 자바 객체 수정만
    // 트랜잭션 commit -> 자동 UPDATE board SET title=? WHERE id=?
}
```

```java
// (2) merge - 반환값을 반드시 받기
@Transactional
public void updateDetached(Board detached) {
    Board managed = em.merge(detached);   // detached 는 여전히 detached!
    managed.setTitle("new");               // managed 의 setter 만 dirty checking 대상
    // 절대 detached.setTitle(...) 하지 말 것.
}
```

```java
// (3) 조회 전용은 readOnly = true
@Transactional(readOnly = true)
public Board getBoard(Long id) {
    return boardRepo.findById(id).orElseThrow();
    // 스냅샷 생성 X, dirty checking 비활성, 불필요한 flush 생략
    // 성능 ↑ 메모리 ↓
}
```

## 면접 한 줄 답변

- **Q. Dirty Checking 의 동작 조건은?** → **managed 상태 + 트랜잭션 안 + commit (또는 flush) 도달** 3 가지 모두 만족.
- **Q. `persist` 와 `merge` 의 차이는?** → **persist** 는 *transient → managed*. **merge** 는 *detached 의 복사본을 managed 로* + *복사본 반환* (원본은 여전히 detached).
- **Q. `flush` 와 `commit` 의 차이는?** → **flush** 는 영속성 컨텍스트의 변경분을 DB 로 *보냄* (트랜잭션 진행 중). **commit** 은 트랜잭션 *종료* (그 직전 자동 flush 도 발생).
- **Q. OSIV 의 trade-off 는?** → **true**: Controller 에서 LAZY 가능, 편함. 단점은 *영속성 컨텍스트·DB 커넥션을 HTTP 응답까지 점유* → 부하 시 커넥션 풀 고갈 위험. **false**: 빠르지만 *DTO 변환 패턴* 필수.

# 2. Quick Reference (실무 복붙)

## 2.1 엔티티 4 상태 표

| 상태 | 정의 | trigger | dirty checking |
|--|--|--|--|
| **transient** | JPA 가 모름 | `new Board()` | X |
| **managed** | 영속성 컨텍스트 등록 | `persist`, `find`, JPQL 결과, `merge` 반환값 | **O** |
| **detached** | 컨텍스트에서 분리 | `detach`, `close`, `clear`, 트랜잭션 종료 | X |
| **removed** | 다음 flush 에 DELETE | `remove` | (UPDATE 대신 DELETE) |

## 2.2 EntityManager 주요 API

| 메서드 | 동작 | 상태 변화 |
|--|--|--|
| `persist(e)` | 영속성 컨텍스트에 등록, INSERT 예약 | transient → managed |
| `find(클래스, PK)` | PK 로 조회 (1차 캐시 HIT 가능) | DB → managed (cache miss) |
| `merge(e)` | detached 의 복사본 영속화, *반환* | (detached) → managed (반환된 복사본) |
| `remove(e)` | DELETE 예약 | managed → removed |
| `detach(e)` | 컨텍스트에서 분리 | managed → detached |
| `clear()` | 컨텍스트 *전체* 초기화 | 모든 managed → detached |
| `close()` | 컨텍스트 종료 | 모든 managed → detached |
| `flush()` | 변경분 DB 로 발송 (트랜잭션은 계속) | 상태 변화 없음 |
| `refresh(e)` | DB 에서 다시 가져와 덮어쓰기 | managed 유지 |

## 2.3 flush 자동 시점

| 시점 | 발생 |
|--|--|
| **트랜잭션 commit 직전** | 가장 흔함, 자동 |
| **JPQL 쿼리 실행 직전** | 정합성 보장 위해. 1차 캐시 미반영분이 SELECT 결과에 빠지지 않도록. |
| **명시적 `em.flush()`** | 드물게 필요 (테스트, 중간 동기화) |

> 예외: `@Transactional(readOnly=true)` 에서는 flush mode 가 `MANUAL`/`COMMIT` 으로 변경되어 JPQL 직전 flush 가 *생략*.

## 2.4 자주 빠지는 함정 모음 (2강)

| 함정 | 정정 |
|--|--|
| `@Transactional` 없는 메서드에서 setter → UPDATE 안 됨 | dirty checking 의 트랜잭션 조건 위반. `@Transactional` 추가 |
| `em.detach()` 후 setter → UPDATE 안 됨 | detached 는 추적 X. `em.merge()` 또는 다시 `find()` |
| `merge(b)` 의 반환값 안 받음 | b 는 여전히 detached. **반환값을 받아 그걸로 작업** |
| 같은 클래스 내 `@Transactional` 메서드 호출 | Spring AOP 프록시 우회. 메서드 분리 또는 self-injection |
| `@Transactional(readOnly=true)` 안에서 setter → 안 됨 | readOnly 가 dirty checking 끔. 수정 의도면 readOnly 빼기 |
| Controller 에서 LAZY 접근 → `LazyInitializationException` (OSIV=false 시) | DTO 변환 패턴 또는 JOIN FETCH (4강) |
| `IDENTITY` 전략인데 *쓰기 지연* 이 안 됨 | PK 받으려고 즉시 INSERT 필수. 어쩔 수 없음 |
| `em.find()` 와 JPQL 결과가 *다를 것* 같지만 1차 캐시 동일 객체 | 의도된 동작. 동일성 보장. |
| `save(b)` 호출 후 `b.setX()` 또 호출 → UPDATE 두 번? | 한 번. 1차 캐시의 같은 row 라 변경분 모아 한 번 UPDATE |
| 트랜잭션 안에서 같은 PK 두 번 `find` → 쿼리 두 번? | 한 번. 두 번째는 1차 캐시 HIT |

# 3. Mind Map (전체 구조 + 체크리스트)

## 3.1 JPA 5강 시리즈 토픽 트리

```
JPA Series
│
├── [1강] 개념 + Entity 매핑
│   └── @Entity / @Id / @Column / enum.STRING / Auditing
│
├── [2강] 영속성 컨텍스트         <- 현재 위치
│   ├── EntityManager + 영속성 컨텍스트
│   │   ├── 1차 캐시 (Map<PK, Entity>)
│   │   ├── 스냅샷 (Dirty Checking 용)
│   │   └── 쓰기 지연 SQL 저장소
│   │
│   ├── 엔티티 4 상태
│   │   ├── transient
│   │   ├── managed
│   │   ├── detached
│   │   └── removed
│   │
│   ├── 동일성 보장 (1차 캐시)
│   │   ├── 같은 PK = 같은 객체
│   │   └── 트랜잭션 경계 = 동일성 경계
│   │
│   ├── Dirty Checking
│   │   ├── 동작 조건 3 가지
│   │   ├── 스냅샷 비교
│   │   └── @DynamicUpdate (변경 컬럼만)
│   │
│   ├── Flush
│   │   ├── 자동 flush 시점 3 가지
│   │   ├── 쓰기 지연 (write-behind)
│   │   ├── IDENTITY 의 제약
│   │   └── flush mode (AUTO / COMMIT)
│   │
│   └── OSIV (Spring 의 패턴)
│       ├── true 의 장단점
│       ├── false 의 장단점

│
├── [3강] Spring Data JPA

├── [4강] 연관관계 매핑
│   └── @ManyToOne / @OneToMany / fetch / N+1 / cascade
│
└── [5강] JPQL + 트랜잭션
    └── JPQL / DTO 매핑 / @Modifying / @Transactional 옵션
```

## 3.2 2강 학습 진도 체크리스트

### 영속성 컨텍스트 정체
- [ ] 영속성 컨텍스트가 *언제* 만들어지고 *언제* 닫히는지 (Spring 기본 + OSIV) 안다
- [ ] 영속성 컨텍스트 *내부의* 세 가지 데이터 구조 (1차 캐시·스냅샷·쓰기 지연 SQL) 를 외운다
- [ ] 영속성 컨텍스트가 *제공하는* 4~5 가지 가치 (1차 캐시·동일성·dirty checking·쓰기 지연·일관성) 를 안다

### 4 상태
- [ ] 4 상태 (transient/managed/detached/removed) 와 각 trigger 를 외운다
- [ ] `persist` 와 `merge` 의 차이를 *반환값* 관점으로 설명 가능
- [ ] Spring Data JPA 의 `save()` 가 내부적으로 `persist` 또는 `merge` 분기하는 것을 안다

### 1차 캐시 / 동일성
- [ ] 같은 트랜잭션 안에서 같은 PK 의 `==` 동일성이 보장됨을 안다
- [ ] 트랜잭션 경계를 넘으면 *별개 객체* 임을 안다
- [ ] `equals`/`hashCode` 작성 시 PK 기반 + getClass().hashCode() 패턴을 안다

### Dirty Checking
- [ ] 동작 조건 3 가지 (managed / 트랜잭션 안 / commit) 외움
- [ ] 스냅샷의 원리 (영속 시점 복사본 vs 현재 비교) 안다
- [ ] `@DynamicUpdate` 의 의미·언제 쓰는지 안다
- [ ] `@Transactional(readOnly=true)` 의 효과 (스냅샷 X, flush mode 변경) 안다

### Flush
- [ ] 자동 flush 시점 3 가지 (commit 직전·JPQL 직전·명시 호출) 외움
- [ ] `flush ≠ commit` 임을 안다
- [ ] 쓰기 지연 (write-behind) 의 원리와 IDENTITY 전략의 제약 안다
- [ ] flush mode AUTO 와 COMMIT 의 차이 안다

### OSIV
- [ ] OSIV 가 무엇이고 Spring Boot 의 기본값 (`true`) 안다
- [ ] true / false 의 trade-off 표 가능
- [ ] `LazyInitializationException` 의 원인과 두 가지 이상 해결책 (DTO 변환·JOIN FETCH) 안다

### 함정
- [ ] 같은 클래스 내 `@Transactional` 호출이 안 되는 이유 (AOP 프록시 우회) 설명 가능
- [ ] `merge` 의 반환값을 무시하면 생기는 버그를 안다

## 3.4 2강 자기 점검 신호

- "save() 안 했는데 어떻게 UPDATE 되지?" 가 *자연스럽게* 답이 나옴 → 통과
- "merge 가 뭐지?" 가 명확해지지 않으면 → Part B 재학습
- "어디까지 LAZY 로 두고 어디서 풀어야 하지?" 가 막히면 → **OSIV + 4 강 fetch 미리 보기**
- 자가점검 7번 (`flush` vs `commit`) 이 헷갈리면 → Part E 재학습
- "왜 같은 클래스 내 @Transactional 호출이 안 돼?" → Spring AOP 프록시 개념 별도 학습 권장
