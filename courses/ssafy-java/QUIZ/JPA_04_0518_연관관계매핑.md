> 14문항. 개념·적용·디버그·면접. 연관관계 주인 · fetch · N+1 · cascade · `@ManyToMany` 함정 자가 진단.

### Q1. (개념) **연관관계의 주인** 이 무엇이며, 정하는 *규칙* 한 줄.

<details><summary>정답</summary>

**연관관계의 주인** = FK 컬럼을 *결정·관리* 하는 쪽. 주인 쪽의 변경만 DB 에 반영. 반대편 (`mappedBy`) 은 *읽기 전용 거울*.

**규칙**: **FK 컬럼이 있는 쪽이 주인**. 보통 `@ManyToOne` 쪽이 주인 (예: `Reply.board`), `@OneToMany` 쪽이 거울 (`Board.replies` + `mappedBy = "board"`).

</details>

---

### Q2. (개념) 4 종 연관관계 어노테이션의 *디폴트 fetch* 와 실무 권장값.

<details><summary>정답</summary>

| 어노테이션 | 스펙 디폴트 | 권장 |
|--|--|--|
| `@ManyToOne` | **EAGER** ❗ | **LAZY** 명시 |
| `@OneToOne` | **EAGER** ❗ | **LAZY** 명시 |
| `@OneToMany` | LAZY | LAZY |
| `@ManyToMany` | LAZY | (애초에 안 씀, 중간 엔티티로 풀기) |

**원칙**: *모든 연관관계에 `fetch = FetchType.LAZY` 명시*. EAGER 는 의도치 않은 JOIN 과 N+1 의 원천.

</details>

### Q3. (개념) **N+1 문제** 의 정의·발생 조건·결과.

<details><summary>정답</summary>

**정의**: 부모 N 개 조회의 **1 쿼리** + 그 결과 row 마다 LAZY 연관 접근으로 인한 **N 개 추가 쿼리**.

**발생 조건**:
- `findAll()` 또는 JPQL 로 부모 N 개 조회
- 루프 안에서 LAZY 연관 (`b.getReplies()`, `r.getBoard()`) 접근
- EAGER 도 N+1 발생 가능 (Hibernate 가 부모 조회 후 *별도 SELECT* 로 연관 로딩)

**결과**: 게시글 1000개 → 1001 쿼리. 운영 환경 DB CPU 100% 박는 주범.

</details>

### Q4. (적용) `Comment` 와 `Post` 가 N:1 관계. `Comment.post_id` 가 FK. 가장 권장되는 매핑을 작성.

<details><summary>정답</summary>

```java
@Entity
public class Post {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;
    // 양방향이 *진짜* 필요하면 추가, 아니면 단방향만으로 충분
}

@Entity
public class Comment {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String content;

    @ManyToOne(fetch = FetchType.LAZY)         // 반드시 LAZY
    @JoinColumn(name = "post_id", nullable = false)
    private Post post;
}
```

핵심:
- `fetch = FetchType.LAZY` **명시** (디폴트 EAGER 함정 회피)
- `@JoinColumn(name = "post_id")` — FK 컬럼명
- `nullable = false` 명시 시 Hibernate 가 *inner join* 으로 최적화 가능

</details>

### Q5. (적용) Q4 의 `Post` 에 *양방향 매핑* 을 추가하시오. cascade·orphanRemoval 까지.

<details><summary>정답</summary>

```java
@Entity
public class Post {
    @Id @GeneratedValue
    private Long id;
    private String title;

    @OneToMany(mappedBy = "post",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Comment> comments = new ArrayList<>();

    // 편의 메서드
    public void addComment(Comment c) {
        comments.add(c);
        c.setPost(this);
    }
}
```

핵심:
- `mappedBy = "post"` — 반대편 (`Comment.post`) 이 주인 선언. 이게 빠지면 별도 중간 테이블 생성됨
- `cascade = CascadeType.ALL` — 부모 작업이 자식에 전파
- `orphanRemoval = true` — 컬렉션에서 빼면 DELETE
- 컬렉션은 `new ArrayList<>()` 로 초기화 — NPE 방지
- **편의 메서드** 로 양쪽 동시 세팅 보장

</details>

### Q6. (적용) `Post` 와 `Comment` 를 한 번의 SELECT 로 가져오는 메서드를 작성하시오. (페이징 X, 단일 부모 + 자식 컬렉션)

<details><summary>정답</summary>

```java
public interface PostRepository extends JpaRepository<Post, Long> {

    @Query("SELECT DISTINCT p FROM Post p LEFT JOIN FETCH p.comments WHERE p.id = :id")
    Optional<Post> findByIdWithComments(@Param("id") Long id);
}
```

핵심:
- `LEFT JOIN FETCH p.comments` — 한 번의 SQL 로 Post + 모든 Comment 가져옴 (N+1 회피)
- `DISTINCT` 필수 — LEFT JOIN 결과의 *row 부풀림* 제거 (Post 1개 + Comment N개 = N row 으로 중복)
- 또는 컬렉션 타입을 `Set<Comment>` 로 (중복 자동 제거)

**EntityGraph 대안**:
```java
@EntityGraph(attributePaths = "comments")
Optional<Post> findById(Long id);
```

</details>

### Q7. (적용) `Student` 와 `Course` 가 N:M 관계인데 *수강 일자* 와 *성적* 도 저장하려고 한다. `@ManyToMany` 직접 사용 대신 어떻게 풀지 코드로.

<details><summary>정답</summary>

**중간 엔티티 패턴**:

```java
@Entity
public class Enrollment {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "student_id", nullable = false)
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "course_id", nullable = false)
    private Course course;

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime enrolledAt;

    private Integer score;   // 성적
}

@Entity
public class Student {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @OneToMany(mappedBy = "student")
    private List<Enrollment> enrollments = new ArrayList<>();
}

@Entity
public class Course {
    @Id @GeneratedValue
    private Long id;
    private String title;

    @OneToMany(mappedBy = "course")
    private List<Enrollment> enrollments = new ArrayList<>();
}
```

`@ManyToMany` 두 개 → `@OneToMany(Enrollment)` + `@ManyToOne` 두 개로 풀기. *항상 이 패턴*.

</details>

### Q8. (적용) 다음 양방향 매핑에 *편의 메서드* 를 추가하시오. add 와 remove 둘 다.

```java
@Entity
public class Board {
    @OneToMany(mappedBy = "board", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Reply> replies = new ArrayList<>();
}
```

<details><summary>정답</summary>

```java
@Entity
public class Board {
    @OneToMany(mappedBy = "board", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Reply> replies = new ArrayList<>();

    public void addReply(Reply r) {
        replies.add(r);
        r.setBoard(this);
    }

    public void removeReply(Reply r) {
        replies.remove(r);
        r.setBoard(null);   // orphanRemoval=true 면 다음 flush 에 DELETE
    }
}
```

핵심:
- add: 양쪽 동시 세팅
- remove: 컬렉션에서 제거 + 자식의 부모 참조 null (`orphanRemoval=true` 가 알아서 DELETE)
- 외부에서는 `b.addReply(r)`, `b.removeReply(r)` 만 호출 — 한쪽만 세팅하는 실수 방지

</details>

### Q9. (디버그) 다음 발언의 무엇이 틀렸나?
> "N+1 문제를 해결하려면 fetch 를 EAGER 로 바꾸면 된다."

<details><summary>정답</summary>

**완전히 틀림. 오히려 EAGER 가 N+1 을 *숨길* 수 있음**.

이유:
- `findAll()` 의 JPQL `SELECT b FROM Board b` 는 *Board 만* 가져옴
- Hibernate 가 EAGER 인 연관 (`b.replies`) 을 *부모 조회 후 별도 SELECT* → 결국 N+1
- 게다가 EAGER 는 *어디서 어떤 JOIN 이 발행되는지 추적 어렵게* 만듦

**올바른 해결**: **LAZY** 기본 + 필요한 곳에서:
- JPQL `JOIN FETCH`
- `@EntityGraph`
- `@BatchSize` (또는 전역 `default_batch_fetch_size`)
- DTO Projection

EAGER 는 *명시적 즉시 로딩 의도* 가 안 보여서 실제 운영 사고 시 진단이 어려움. LAZY + 명시적 fetch 가 *문제 발견 가능성* 도 더 높음.

</details>

### Q10. (디버그) 다음 메서드의 *치명적 함정* 을 지적하시오.
```java
@Query("SELECT b FROM Board b LEFT JOIN FETCH b.replies WHERE b.categoryId = :cid")
Page<Board> findByCategoryWithReplies(@Param("cid") Long cid, Pageable pageable);
```

<details><summary>정답</summary>

**함정**: **`OneToMany` JOIN FETCH + 페이징 (`Pageable`)** 동시 사용.

원인:
- `LEFT JOIN FETCH b.replies` 는 *Board 한 개 + Reply N 개 = N row* 로 결과를 만듦 (row 부풀림)
- 페이징의 `LIMIT/OFFSET` 은 *row 단위* 자름 → Board 가 *완전 로딩 안 됨* (일부 댓글만 잘림)
- Hibernate 는 이를 감지하고 **메모리 페이징 fallback**: 전체 결과를 메모리로 가져와 페이징 → **데이터 폭증 시 OOM**

해결:
1. **DTO Projection** (최선):
   ```java
   @Query("SELECT new com.example.dto.BoardSummary(b.id, b.title) FROM Board b WHERE b.categoryId = :cid")
   Page<BoardSummary> findByCategoryAsDto(@Param("cid") Long cid, Pageable pageable);
   ```
2. **두 쿼리로 분리** + `@BatchSize`
3. **`@OneToOne` 이나 `@ManyToOne` 의 JOIN FETCH** 는 페이징 OK (row 안 부풂)

</details>

### Q11. (디버그) 다음 양방향 매핑이 *예상치 못한 SQL* 을 발생시킨다. 무엇이 잘못됐나?
```java
@Entity
public class Board {
    @Id @GeneratedValue
    private Long id;

    @OneToMany    // (?)
    @JoinColumn(name = "board_id")
    private List<Reply> replies;
}

@Entity
public class Reply {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne
    @JoinColumn(name = "board_id")
    private Board board;
}
```

<details><summary>정답</summary>

**문제**: `@OneToMany` 에 `mappedBy` 가 *없음*. 그리고 `@ManyToOne` 에도 매핑이 있음 → **양쪽 다 주인** 으로 해석.

결과: Reply 저장 시 **두 단계** 가 발행:
1. `INSERT INTO reply (..., board_id) VALUES (...)` — `Reply.board` 의 매핑
2. `UPDATE reply SET board_id = ? WHERE id = ?` — `Board.replies` 의 `@JoinColumn` 매핑

같은 FK 컬럼을 *두 번* 업데이트하는 비효율.

**수정**: `Board` 의 `@OneToMany` 에 **`mappedBy = "board"` 추가**, `@JoinColumn` 제거:

```java
@Entity
public class Board {
    @OneToMany(mappedBy = "board")   // 거울임을 선언
    private List<Reply> replies;
}
```

**원칙**: 양방향 매핑 시 *항상* `mappedBy` 명시. 주인은 `@ManyToOne` (FK 가 있는 쪽).

</details>

### Q12. (디버그) 다음 매핑의 *위험한 부분* 을 지적하시오.
```java
@Entity
public class User {
    @OneToMany(mappedBy = "owner",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Tag> tags;
}

@Entity
public class Tag {
    @ManyToOne(fetch = FetchType.LAZY)
    private User owner;
    // 다른 곳에서도 Tag 를 참조 - Post.tags, Article.tags 등
}
```

<details><summary>정답</summary>

**문제**: `cascade = CascadeType.ALL + orphanRemoval = true` 가 **공유 자식** 에 적용됨.

`Tag` 가 `User` 외에도 `Post`, `Article` 등 *다른 곳에서 참조* 됨. 그런데:
- `User` 가 삭제되면 cascade=REMOVE 로 모든 Tag 가 DELETE → 다른 객체가 참조하던 Tag 도 사라짐 → **데이터 무결성 깨짐**
- User.tags 에서 한 Tag 가 빠지면 orphanRemoval 로 DELETE → 같은 Tag 가 Post 에 있어도 사라짐

**원칙**: cascade=ALL + orphanRemoval=true 는 **자식이 부모에 *독점적으로* 묶일 때만** 안전. DDD 의 *Aggregate Root* 가 자연스럽게 부합.

**수정**:
```java
// 옵션 1: cascade·orphanRemoval 제거 (Tag 는 독립 생명주기)
@ManyToMany 또는 중간 엔티티 패턴으로 변경

// 옵션 2: Tag 가 정말 User 의 *전유물* 이라면 다른 곳의 참조 제거
```

</details>

### Q13. (면접) "JPA 의 N+1 문제는 어떻게 해결하시나요?" 면접 단골. 4 가지 방법과 *선택 기준* 으로 답변.

<details><summary>정답</summary>

**4 가지 해결책 + 선택 기준**:

1. **JPQL `JOIN FETCH`**
   - 한 쿼리로 부모 + 자식 로딩
   - **제약**: `OneToMany` + 페이징 동시 사용 금지 (메모리 페이징 fallback)
   - 단건·소량 부모에 가장 흔히 사용

2. **`@EntityGraph(attributePaths = ...)`**
   - JPQL 없이 메서드 이름 규칙·기본 메서드에 적용
   - 내부적으로 JOIN FETCH 와 동등
   - 여러 메서드에서 같은 fetch 패턴 재사용에 편함

3. **`@BatchSize` (또는 전역 `default_batch_fetch_size`)**
   - LAZY 연관 접근 시 *N 개를 IN 절로 묶어* 한 번에 가져옴
   - **페이징과 함께 사용 가능** (row 안 부풂)
   - 1 + ceil(N/batchSize) 쿼리

4. **DTO Projection**
   - `SELECT new pkg.DTO(...)` 또는 Interface-based Projection
   - 엔티티 자체를 안 가져오므로 LAZY 함정 자체가 없음
   - 페이징·대규모에 가장 안전

**선택 기준**:
- 단순 단건 + 자식 컬렉션 → **JOIN FETCH**
- **페이징** 필요 + 자식 컬렉션 → **DTO Projection** 또는 **@BatchSize**
- 여러 곳에서 같은 fetch → **@EntityGraph**
- 전역 default → **`default_batch_fetch_size`** 설정

</details>

### Q14. (면접) "`@ManyToMany` 직접 사용을 왜 권장하지 않나요?"

<details><summary>정답</summary>

**세 가지 이유**:

1. **중간 테이블에 *추가 컬럼* 추가 불가능 / 어려움**
   - 수강 관계라면 *수강일, 성적, 상태* 같은 메타 정보가 필연적으로 생김
   - `@ManyToMany` 는 단순 join 테이블만 → 이런 정보 둘 곳이 없음

2. **발행 SQL 추적 어려움**
   - join 테이블이 *암묵적* — 디버깅이 까다로움
   - cascade·orphanRemoval 의도와 어긋나는 SQL 발행 빈번

3. **확장성 제로**
   - 처음 단순 N:M 이라도 *95% 는 나중에 메타 정보가 추가됨*. 그때 가서 중간 엔티티로 마이그레이션 = 비용 큼

**대안**: **항상 처음부터 중간 엔티티**.

```java
@ManyToMany → @OneToMany(중간) + @ManyToOne 두 개
```

이 패턴은:
- 추가 컬럼 자유롭게
- 명시적 엔티티 → SQL·cascade 명확
- 검색·쿼리 자연스러움 (`enrollmentRepo.findByStudentId(...)`)

</details>
