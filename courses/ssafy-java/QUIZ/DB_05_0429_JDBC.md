### Q1. (개념) JDBC 4단계 정형 코드와 각 단계의 책임?

<details><summary>정답</summary>

```java
try (Connection con = DriverManager.getConnection(URL, USER, PW);  // 1 연결
     PreparedStatement ps = con.prepareStatement(sql);              // 2 준비
     ResultSet rs = ps.executeQuery()) {                            // 3 실행
    while (rs.next()) {                                              // 4 순회
        Board b = new Board(rs.getLong("id"), rs.getString("title"));
        list.add(b);
    }
}
```

| 단계 | 책임 | 비용 |
|--|--|--|
| 1. Connection | TCP 연결 + 인증 | 수십 ms |
| 2. PreparedStatement | SQL 컴파일 + 파라미터 바인딩 | ms |
| 3. ResultSet | DB 가 반환한 결과 행 커서 | - |
| 4. close | 모든 리소스 해제 | 누수 방지 |

→ `Connection` 이 비싸기 때문에 실무에선 **커넥션 풀** (HikariCP) 로 재사용.

</details>

### Q2. (개념) Statement vs PreparedStatement 의 2가지 차이?

<details><summary>정답</summary>

| | Statement | PreparedStatement |
|--|--|--|
| **SQL Injection** | 취약 (문자열 concat) | **자동 escape 로 방어** |
| **성능** | 매번 SQL 파싱·컴파일 | 컴파일 결과 **재사용** |
| **가독성** | `"... WHERE id = '" + x + "'"` | `"... WHERE id = ?"` + `setString(1, x)` |
| **타입** | 항상 String | `setInt/setLong/setString/setDate` 등 정확한 타입 |

**SQL Injection 예시**:
```java
// 안 좋은 예 - userInput = "' OR '1'='1"
String sql = "SELECT * FROM users WHERE id = '" + userInput + "'";
// 실제 실행: SELECT * FROM users WHERE id = '' OR '1'='1' → 전체 노출

// 좋은 예
PreparedStatement ps = con.prepareStatement(
    "SELECT * FROM users WHERE id = ?");
ps.setString(1, userInput);   // ' 가 자동 escape
```

**원칙**: 모든 SQL 은 PreparedStatement. Statement 는 동적 DDL 같은 특수 케이스에만.

</details>

### Q3. (개념) try-with-resources 가 리소스 누수를 막는 원리?

<details><summary>정답</summary>

`try ( ... )` 괄호 안에 선언된 모든 **AutoCloseable 객체** 를 try 블록 종료 시 **선언 역순으로 `close()` 자동 호출**. **예외가 발생해도 보장**.

```java
try (Connection con = ...;           // 1
     PreparedStatement ps = ...;     // 2
     ResultSet rs = ps.executeQuery()) {  // 3
    // 작업
}
// 자동으로: rs.close() → ps.close() → con.close()
// 어디서 예외가 나도 close 보장
```

**왜 역순?**: 안쪽 자원 (rs) 이 바깥 자원 (ps, con) 에 의존하므로 안쪽을 먼저 닫아야 안전.

**옛 finally 방식의 문제**:
```java
Connection con = null;
try {
    con = DriverManager.getConnection(...);
    // ...
} catch (SQLException e) { ... }
finally {
    if (con != null) try { con.close(); } catch (SQLException e) {}
    // PS, RS 까지 하면 5단계 중첩
}
```

→ JDK 7+ try-with-resources 가 표준.

</details>

### Q4. (개념) `executeQuery()`, `executeUpdate()`, `execute()` 의 차이?

<details><summary>정답</summary>

| 메서드 | 반환 | 용도 |
|--|--|--|
| `executeQuery()` | `ResultSet` | SELECT (결과 행이 있는 SQL) |
| `executeUpdate()` | `int` (영향 행 수) | INSERT, UPDATE, DELETE, DDL |
| `execute()` | `boolean` (true=ResultSet, false=count) | 결과 타입 모를 때 (동적 SQL) |

```java
// SELECT
ResultSet rs = ps.executeQuery();
while (rs.next()) { ... }

// INSERT / UPDATE / DELETE
int affected = ps.executeUpdate();
System.out.println(affected + " 행 변경됨");

// 동적 (실무에선 거의 안 씀)
boolean hasResultSet = ps.execute();
if (hasResultSet) { ResultSet rs = ps.getResultSet(); }
else              { int count = ps.getUpdateCount(); }
```

⚠️ SELECT 인데 `executeUpdate()` 호출 → `SQLException: Can not issue SELECT via executeUpdate()`.

</details>

### Q5. (적용) boards 테이블에서 제목으로 검색하는 DAO 메서드 (PreparedStatement + ResultSet).

<details><summary>정답</summary>

```java
public List<Board> findByTitle(String keyword) throws SQLException {
    String sql = "SELECT id, title, content, created_at "
               + "FROM boards WHERE title LIKE ? ORDER BY id DESC";

    List<Board> list = new ArrayList<>();
    try (Connection con = DriverManager.getConnection(URL, USER, PW);
         PreparedStatement ps = con.prepareStatement(sql)) {

        ps.setString(1, "%" + keyword + "%");   // 1-base, LIKE 와일드카드는 값에

        try (ResultSet rs = ps.executeQuery()) {
            while (rs.next()) {
                Board b = new Board();
                b.setId(rs.getLong("id"));
                b.setTitle(rs.getString("title"));
                b.setContent(rs.getString("content"));
                b.setCreatedAt(rs.getTimestamp("created_at").toLocalDateTime());
                list.add(b);
            }
        }
    }
    return list;
}
```

**핵심**:
- LIKE 와일드카드 `%` 는 SQL 이 아니라 **값에 포함** (`"%" + keyword + "%"`)
- PS 파라미터 인덱스는 **1-base** (자바 배열과 다름)
- 컬럼 접근은 **이름** 으로 (`rs.getString("title")` → 컬럼 순서 변경에 안전)

</details>

### Q6. (적용) INSERT 후 DB 가 자동 생성한 PK (AUTO_INCREMENT) 받기.

<details><summary>정답</summary>

```java
String sql = "INSERT INTO boards (title, content) VALUES (?, ?)";

try (Connection con = DriverManager.getConnection(URL, USER, PW);
     PreparedStatement ps = con.prepareStatement(
         sql,
         Statement.RETURN_GENERATED_KEYS)) {    // 핵심 옵션

    ps.setString(1, "제목");
    ps.setString(2, "본문");
    ps.executeUpdate();

    try (ResultSet keys = ps.getGeneratedKeys()) {
        if (keys.next()) {
            long newId = keys.getLong(1);       // 자동 생성된 ID
            System.out.println("새 게시글 ID: " + newId);
        }
    }
}
```

**왜 필요한가**:
- 게시글 작성 후 상세 페이지로 리다이렉트 → ID 필요
- 부모-자식 INSERT (게시글 + 첨부 파일) → 부모 ID 를 자식 INSERT 에 사용

⚠️ 옵션 없이 호출하면 `getGeneratedKeys()` 가 빈 ResultSet 반환.

</details>

### Q7. (적용) JDBC 로 송금 트랜잭션 (A 차감 + B 추가).

<details><summary>정답</summary>

```java
Connection con = null;
try {
    con = DriverManager.getConnection(URL, USER, PW);
    con.setAutoCommit(false);            // 1. 수동 모드 시작

    // 2. A 차감
    try (PreparedStatement ps1 = con.prepareStatement(
            "UPDATE accounts SET balance = balance - ? WHERE id = ?")) {
        ps1.setBigDecimal(1, new BigDecimal("1000"));
        ps1.setString(2, "A");
        ps1.executeUpdate();
    }

    // 3. B 추가
    try (PreparedStatement ps2 = con.prepareStatement(
            "UPDATE accounts SET balance = balance + ? WHERE id = ?")) {
        ps2.setBigDecimal(1, new BigDecimal("1000"));
        ps2.setString(2, "B");
        ps2.executeUpdate();
    }

    con.commit();                        // 4. 모두 성공 -> 영구 반영
} catch (SQLException e) {
    if (con != null) con.rollback();     // 5. 한쪽 실패 -> 둘 다 취소
    throw e;
} finally {
    if (con != null) {
        con.setAutoCommit(true);         // 풀에 반환 전 기본값 복원
        con.close();
    }
}
```

**기본**: JDBC 의 `autoCommit = true` (모든 SQL 즉시 commit). 송금처럼 묶음이 필요한 작업은 `false` 로.

→ Spring `@Transactional` 이 이 코드를 어노테이션으로 추상화한 것.

</details>

### Q8. (적용) `IN (?, ?, ?, ...)` 의 파라미터 개수가 동적일 때 PreparedStatement 작성.

<details><summary>정답</summary>

```java
public List<Board> findByIds(List<Long> ids) throws SQLException {
    if (ids.isEmpty()) return Collections.emptyList();

    // 1. ? N 개 동적 생성
    String placeholders = ids.stream()
        .map(i -> "?")
        .collect(Collectors.joining(","));      // "?,?,?"

    String sql = "SELECT * FROM boards WHERE id IN (" + placeholders + ")";

    try (Connection con = DriverManager.getConnection(URL, USER, PW);
         PreparedStatement ps = con.prepareStatement(sql)) {

        // 2. 1-base 로 바인딩
        for (int i = 0; i < ids.size(); i++) {
            ps.setLong(i + 1, ids.get(i));
        }

        try (ResultSet rs = ps.executeQuery()) {
            // ...
        }
    }
}
```

**주의**:
- DB 별 IN 절 길이 제한 (Oracle 1000 개, MySQL 디폴트 1024)
- 매우 많으면 임시 테이블 + JOIN, 또는 배치 chunking (500개씩)
- 절대 `ids` 를 문자열 concat 하면 안 됨 (SQL Injection)

</details>

### Q9. (디버그) DB 에 저장한 `2026-05-20 15:00:00` 이 자바에서 조회하면 `2026-05-20 06:00:00` 으로 9시간 어긋남. 원인과 해결?

<details><summary>정답</summary>

**원인**: DB 와 JVM 의 **타임존 불일치**.
- DB 서버: UTC (예: AWS RDS 기본)
- JVM: 기본 시스템 시간대 (KST)
- TIMESTAMP 컬럼 → UTC 로 저장 → JVM 이 잘못된 시간대로 해석

**해결 3 단계**:

```java
// 1. JDBC URL 에 serverTimezone 명시
String URL = "jdbc:mysql://localhost:3306/mydb"
           + "?serverTimezone=Asia/Seoul"
           + "&useUnicode=true&characterEncoding=UTF-8"
           + "&useSSL=false";

// 2. JVM 옵션
// -Duser.timezone=Asia/Seoul

// 3. DB 서버 자체 설정 통일 (my.cnf)
// default-time-zone = '+09:00'
```

**Bonus**: 가능하면 **UTC 로 저장**, 표시할 때만 사용자 시간대로 변환 (`ZonedDateTime`). 글로벌 서비스 표준.

</details>

### Q10. (디버그) `rs.getString(1)` 과 `rs.getString("title")` 의 차이와 권장?

<details><summary>정답</summary>

| 방식 | 장점 | 단점 |
|--|--|--|
| `rs.getString(1)` (1-base 인덱스) | 약간 빠름 (이름 검색 X) | **컬럼 순서 바뀌면 깨짐** |
| `rs.getString("title")` (이름) | SQL 컬럼 순서·추가에 안전 | 이름 lookup 비용 (무시 가능) |

```sql
-- 처음
SELECT id, title FROM boards;
-- rs.getString(1) = id
-- rs.getString(2) = title

-- 나중에 SELECT 컬럼 순서 변경
SELECT title, id FROM boards;
-- rs.getString(1) 이 갑자기 title 반환 -> 런타임 에러 또는 잘못된 데이터
```

**권장**: **항상 컬럼명**. 성능 차이는 무시 가능하고, 유지보수성이 훨씬 큼.

추가:
- ResultSet 컬럼 인덱스도 PS 파라미터처럼 **1-base** (자바 배열 0-base 와 다름)
- 컬럼 alias 가 있으면 alias 로 접근 (`SELECT title AS t` -> `rs.getString("t")`)

</details>

### Q11. (디버그) 다음 코드의 누수 위치와 수정?

```java
Connection con = DriverManager.getConnection(URL, USER, PW);
PreparedStatement ps = con.prepareStatement("SELECT * FROM users");
ResultSet rs = ps.executeQuery();
while (rs.next()) {
    System.out.println(rs.getString("name"));
}
con.close();
```

<details><summary>정답</summary>

**누수 위치**:
- `rs.close()` 안 호출됨
- `ps.close()` 안 호출됨
- 예외 발생 시 `con.close()` 도 안 됨

**문제**:
- ResultSet/Statement 가 일부 풀에서 캐싱 → 누수 누적
- 예외 발생 시 Connection 이 풀에 반환 안 됨 → 풀 고갈 → 서비스 정지

**수정 (try-with-resources)**:
```java
try (Connection con = DriverManager.getConnection(URL, USER, PW);
     PreparedStatement ps = con.prepareStatement("SELECT * FROM users");
     ResultSet rs = ps.executeQuery()) {

    while (rs.next()) {
        System.out.println(rs.getString("name"));
    }
}
// 자동으로 rs -> ps -> con 순서로 close
// 예외 발생해도 보장
```

운영 사고: 누수 100건/일 누적 → 일주일 안에 `Connection pool exhausted` → 전체 장애.

</details>

### Q12. (디버그) PreparedStatement 의 `?` 인덱스가 자바 배열과 다른 점 + 흔한 실수.

<details><summary>정답</summary>

| | 인덱스 | 예 |
|--|--|--|
| 자바 배열 | **0-base** | `arr[0]` = 첫 번째 |
| PS 파라미터 | **1-base** | `ps.setString(1, ...)` = 첫 `?` |
| ResultSet 컬럼 | **1-base** | `rs.getString(1)` = 첫 컬럼 |

**흔한 실수**:
```java
String sql = "SELECT * FROM boards WHERE title = ? AND author = ?";
PreparedStatement ps = con.prepareStatement(sql);

// 안 좋은 예 - 자바 배열 감각으로 0 부터
ps.setString(0, "제목");     // SQLException: Parameter index out of range (0 < 1)

// 좋은 예
ps.setString(1, "제목");
ps.setString(2, "작성자");
```

**왜 1-base?**: JDBC API 설계자가 **SQL/DB 관례** (Oracle, MS SQL 모두 1-base) 에 맞춤. 자바 배열과 다르지만, **DB 세계의 표준**.

→ for 루프 작성 시 `i + 1` 로 변환 필요 (Q8 예제 참조).

</details>

### Q13. (개념) Connection Pool (HikariCP) 가 필요한 이유와 동작 원리?

<details><summary>정답</summary>

**이유**: `DriverManager.getConnection()` 은 매번 **TCP 연결 + 인증** → 수십 ms.

| 시나리오 | 비용 |
|--|--|
| 단일 요청 (개발 환경) | 무시 가능 |
| 100 req/sec (운영) | 매 요청마다 100ms → 동시 처리 불가, 서버 죽음 |

**Pool 동작**:
```
[앱]                          [Pool (HikariCP)]                [DB]
 |                                  |                          |
 |--ds.getConnection()------------->|                          |
 |                                  |--미리 만든 con 빌려줌---->|
 |<--Connection (재사용)-----------|                          |
 |                                  |                          |
 |--사용 후 con.close()------------>|                          |
 |                                  |--TCP 끊지 않고 풀로 반환  |
```

**설정** (Spring Boot 기본 HikariCP):
```yaml
spring.datasource.hikari:
  maximum-pool-size: 10          # 풀 최대 크기
  minimum-idle: 5                # 유휴 최소
  connection-timeout: 30000      # 대기 30초
  max-lifetime: 1800000          # 30분 후 재생성
```

**`con.close()` 의 의미**: 진짜 닫는 게 아니라 **풀에 반환**. try-with-resources 가 안전.

→ 모든 실무 자바 앱은 풀 사용. JNDI/HikariCP/DBCP 등.

</details>

### Q14. (면접) "JDBC, JdbcTemplate, MyBatis, JPA 의 차이를 추상화 단계로 설명하시오."

<details><summary>정답</summary>

**추상화 사다리** (낮음 → 높음):

| 도구 | 책임 | 코드량 | 학습 곡선 |
|--|--|--|--|
| **JDBC (raw)** | 자바 표준 SQL API | 매우 많음 (try-with-res, RowMapper 수동) | 낮음 |
| **JdbcTemplate** (Spring) | JDBC 보일러플레이트 제거 | 적음 | 낮음 |
| **MyBatis** | XML/어노테이션으로 SQL 분리 + 매핑 | 적음 | 중간 |
| **Spring Data JPA** | 객체 그래프 ↔ 테이블 자동 매핑 (ORM) | 매우 적음 (메서드 이름으로 쿼리) | 높음 |

**JdbcTemplate 예** (JDBC 대비 1/5 코드):
```java
List<Board> list = jdbcTemplate.query(
    "SELECT id, title FROM boards WHERE author = ?",
    (rs, rowNum) -> new Board(rs.getLong("id"), rs.getString("title")),
    "kim");
```

**MyBatis 예**:
```xml
<select id="findByAuthor" resultType="Board">
    SELECT id, title FROM boards WHERE author = #{author}
</select>
```
```java
List<Board> list = boardMapper.findByAuthor("kim");
```

**JPA 예**:
```java
List<Board> list = boardRepository.findByAuthor("kim");
// 메서드 이름만으로 SELECT * FROM board WHERE author = ?
```

**선택 기준**:
- 복잡한 SQL 직접 작성 + DBA 와 협업 → **MyBatis**
- 객체 중심 도메인 모델 + 빠른 개발 → **JPA**
- 단순 CRUD + 미세 제어 → **JdbcTemplate**
- 학습·디버깅·레거시 → **JDBC**

**공통 기반**: 모두 결국 **JDBC 위에 추상화**. 트랜잭션, 풀, 예외 분류는 동일. 그래서 JDBC 를 알아야 어느 도구든 깊게 이해 가능.

</details>
