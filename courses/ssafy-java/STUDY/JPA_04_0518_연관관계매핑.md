# JPA 4강: 연관관계 매핑

> **이 강의는 무엇인가**: 객체의 *참조*·*컬렉션* 을 RDB 의 *FK* 로 매핑하는 방법. `@ManyToOne`, `@OneToMany`, `@OneToOne`, `@ManyToMany`. 연관관계의 *주인* (`mappedBy`), fetch 전략 (`LAZY`/`EAGER`), **N+1 문제**, cascade, orphanRemoval.
> **왜 배우는가**: JPA 의 진정한 가치 — 그리고 **가장 자주 망가지는 영역**. 실무에서 JPA 가 *느리다* 는 불만의 80% 는 이 단원의 함정. 면접 단골 + 운영 사고 단골.

---

## 들어가기 전에

- **선수**: 1 강 (Entity 매핑), 2 강 (영속성 컨텍스트), 3 강 (Spring Data JPA).
- **마인드셋**: "**객체는 두 방향**, **DB 는 한 방향 (FK)**." 이 비대칭을 *주인* 개념으로 흡수.
- **본 강 5 가지 원칙** (외워두면 함정 80% 회피):
  1. 모든 연관관계는 **LAZY** 기본
  2. `@OneToMany` 단방향 X — 항상 `@ManyToOne` 부터 시작
  3. 양방향이 필요할 때만 양방향, *주인은 `@ManyToOne` 쪽*
  4. `@ManyToMany` 직접 사용 X — 중간 엔티티로 풀기
  5. **JOIN FETCH + OneToMany + 페이징 동시 사용 금지**

# Part A. 왜 연관관계 매핑이 어려운가

## 1. 객체와 테이블의 비대칭

```
[객체]                               [테이블]
class Board {                        board
  List<Reply> replies;               +-----+----+
}                                    | id  | ...|
                                     +-----+----+
class Reply {
  Board board;                       reply
}                                    +-----+----------+
                                     | id  | board_id |
                                     +-----+----------+
                                                ^
                                                FK
```

| | 객체 | 테이블 |
|--|--|--|
| 방향 | **양방향** (`board.getReplies()`, `reply.getBoard()`) | **한 방향** (`reply.board_id` 만) |
| 표현 | 참조 (`board`) + 컬렉션 (`List<Reply>`) | FK 컬럼 한 개 |
| 일관성 | 양쪽 코드에서 모두 챙겨야 | DB 가 알아서 |

JPA 는 이 비대칭을 **연관관계 주인** 개념으로 해결. *주인 쪽* 이 FK 를 *책임*, 반대편은 *읽기 전용 거울*.

## 2. 함정의 출처

이 단원의 함정 대부분은 다음 셋 중 하나:

1. **주인을 잘못 정함** → 의도와 다른 SQL 발행 (UPDATE 추가, N+1 등)
2. **fetch 전략을 무의식적으로 EAGER** → 의도치 않은 JOIN, LAZY 보다 *나쁜* 성능
3. **JOIN FETCH 와 페이징 조합** → 메모리 페이징 fallback → OOM

이 셋을 매번 의식하면 90% 해결.

# Part B. `@ManyToOne` — 가장 흔하고 단순한 시작

## 1. 단방향 N:1

게시글 (Board) - 댓글 (Reply) 관계. *댓글이 게시글을 가리킴*.

```java
@Entity
public class Reply {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String content;

    @ManyToOne(fetch = FetchType.LAZY)         // *반드시* LAZY
    @JoinColumn(name = "board_id")             // FK 컬럼명
    private Board board;
}

@Entity
public class Board {
    @Id @GeneratedValue
    private Long id;
    private String title;
    // 댓글 컬렉션은 *아직 매핑 안 함* (단방향)
}
```

DB 결과:
```sql
CREATE TABLE board ( id BIGINT PRIMARY KEY, title VARCHAR(200), ... );
CREATE TABLE reply (
    id BIGINT PRIMARY KEY,
    content VARCHAR(1000),
    board_id BIGINT,
    FOREIGN KEY (board_id) REFERENCES board(id)
);
```

## 2. 사용

```java
// 게시글 + 댓글 추가
Board b = boardRepo.findById(1L).orElseThrow();
Reply r = new Reply();
r.setContent("좋네요");
r.setBoard(b);                  // 객체 참조
replyRepo.save(r);              // INSERT reply(content=?, board_id=?)
```

```java
// 댓글에서 게시글 조회
Reply r = replyRepo.findById(10L).orElseThrow();
Board b = r.getBoard();         // LAZY: 이 시점에 SELECT 발행
System.out.println(b.getTitle());
```

## 3. `@ManyToOne` 의 기본 옵션

| 옵션 | 기본값 | 권장 |
|--|--|--|
| `fetch` | `EAGER` (스펙 디폴트) | **`LAZY`** 강력 권장 |
| `optional` | `true` | FK 가 NULL 허용. NOT NULL 이면 `false` 로 명시 (Hibernate 가 inner join 최적화) |
| `cascade` | `{}` | 부모 → 자식 전파만 거의 안 함 (`@OneToMany` 쪽에서) |

> **함정**: `@ManyToOne` 의 디폴트는 *EAGER*. **반드시 `fetch = FetchType.LAZY` 명시**.

# Part C. `@OneToMany` 와 양방향

## 1. 양방향이 *필요한가*?

먼저 자문: **`board.getReplies()` 가 정말 필요한가?**

대부분의 경우 **단방향 (`Reply.board`) 만으로 충분**. 댓글 조회는 `replyRepo.findByBoard(b)` 로.

양방향이 *진짜* 필요한 경우:
- 부모 객체에서 자식 컬렉션을 *자주* 탐색
- cascade·orphanRemoval 로 부모 → 자식 자동 전파 필요
- DDD 의 Aggregate 패턴 (부모가 자식을 관리)

## 2. 양방향 추가

```java
@Entity
public class Board {
    @Id @GeneratedValue
    private Long id;
    private String title;

    @OneToMany(mappedBy = "board",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private List<Reply> replies = new ArrayList<>();
}
```

핵심 한 줄: `mappedBy = "board"`. 이게 **"나는 주인 아님, 반대편 Reply 의 `board` 필드가 주인"** 선언.

DB 는 변화 없음 — 여전히 `reply.board_id` FK 만. `Board` 의 `replies` 필드는 *메모리 거울*.

## 3. 사용

```java
// 양방향 - 부모에서 자식 추가
Board b = boardRepo.findById(1L).orElseThrow();
b.getReplies().size();    // LAZY: SELECT * FROM reply WHERE board_id = 1
```

# Part D. 연관관계의 주인 (mappedBy)

## 1. 주인의 역할

**연관관계의 주인** = FK 컬럼을 *결정·관리* 하는 쪽. 다음만 *주인* 의 변경이 DB 에 반영:

- `INSERT` 시 FK 값 결정
- `UPDATE` 시 FK 값 변경

반대편 (`mappedBy` 가 있는 쪽) 의 변경은 **DB 에 반영되지 않음**.

## 2. 주인 정하는 규칙

> **FK 가 있는 쪽이 주인**

- `Reply.board_id` 컬럼이 있으므로 → `Reply.board` (`@ManyToOne` 쪽) 가 주인
- `Board.replies` 는 *컬렉션* 거울 → `mappedBy = "board"` 명시

## 3. `mappedBy` 빼면?

```java
// 잘못된 예 - 양쪽 다 주인
@Entity
public class Reply {
    @ManyToOne
    @JoinColumn(name = "board_id")
    private Board board;
}

@Entity
public class Board {
    @OneToMany    // mappedBy 없음!
    private List<Reply> replies;
}
```

JPA 가 *양쪽 다 주인* 으로 해석 → **두 종류의 SQL 발행** :
- `Reply.board` 가 `INSERT/UPDATE reply.board_id`
- `Board.replies` 가 **별도의 중간 테이블** (예: `board_replies(board_id, reply_id)`) 을 만들어 INSERT

테이블 의도와 어긋나고 SQL 중복.

**원칙**: 양방향 매핑 시 *항상* `mappedBy` 명시.

## 4. 주인을 *틀린 쪽* 으로 정하면?

```java
// 가능하지만 비추 - @OneToMany 가 주인
@Entity
public class Board {
    @OneToMany
    @JoinColumn(name = "board_id")    // mappedBy 없이 JoinColumn
    private List<Reply> replies;
}
```

- 가능하긴 함 (`@JoinColumn` 으로 FK 위치 명시)
- 그러나 *Reply 를 저장* 할 때 `INSERT` 후 *별도 UPDATE* 로 board_id 채우는 비효율 발생
- 권장: **`@ManyToOne` 쪽이 주인**.

# Part E. fetch 전략 — LAZY vs EAGER

## 1. 정의

```java
@ManyToOne(fetch = FetchType.LAZY)   // 권장
@ManyToOne(fetch = FetchType.EAGER)  // 비추 (스펙 디폴트)
```

- **LAZY**: 연관 객체를 *접근* 하는 시점에 별도 SELECT
- **EAGER**: *부모 조회* 시 함께 JOIN 또는 별도 SELECT

## 2. 디폴트값

| 어노테이션 | 스펙 디폴트 |
|--|--|
| `@ManyToOne` | **EAGER** (함정!) |
| `@OneToOne` | **EAGER** (함정!) |
| `@OneToMany` | LAZY |
| `@ManyToMany` | LAZY |

> **함정**: `@ManyToOne` 과 `@OneToOne` 이 *디폴트 EAGER*. **모든 연관관계에 명시적으로 `fetch = FetchType.LAZY`** 권장.

## 3. LAZY 의 동작

```java
Reply r = replyRepo.findById(10L).orElseThrow();
// SELECT * FROM reply WHERE id = 10
// 이 시점에 r.board 는 **Hibernate Proxy** 객체. 실제 Board 데이터 X.

r.getBoard().getTitle();
// 프록시의 메서드 호출 → SELECT * FROM board WHERE id = ?
// 실제 데이터 로딩
```

LAZY 의 매커니즘: Hibernate 가 *동적 프록시* 객체를 만들어 `r.board` 자리에 넣어두고, 메서드 호출 시점에 DB 조회.

## 4. EAGER 가 위험한 이유

```java
@ManyToOne(fetch = FetchType.EAGER)
private Board board;

@ManyToOne(fetch = FetchType.EAGER)
private Category category;
```

`replyRepo.findById(10L)` 한 번에:
```sql
SELECT r.*, b.*, c.*
FROM reply r
LEFT JOIN board b ON r.board_id = b.id
LEFT JOIN category c ON r.category_id = c.id
WHERE r.id = 10
```

문제:
1. **불필요한 JOIN** — board/category 가 필요 없을 때도 가져옴
2. **N+1 잠재** — JPQL/Repository 에서 `findAll()` 시 *각 row 마다 추가 SELECT* 발생 가능
3. **페이징 + EAGER OneToMany** → 메모리 페이징 fallback (Part F)

**원칙**: EAGER 는 거의 사용하지 않음. 필요할 때마다 `JOIN FETCH` 로 *명시적* 즉시 로딩.

# Part F. N+1 문제 — JPA 면접 최고 단골

## 1. 현상

```java
List<Board> boards = boardRepo.findAll();      // (1) SELECT * FROM board → 게시글 10개
for (Board b : boards) {
    System.out.println(b.getReplies().size()); // (N) 각 게시글마다 SELECT FROM reply WHERE board_id = ?
}
// 총 1 + N = 11 번 쿼리. 게시글 1000개면 1001번.
```

**N+1**: 1 번의 쿼리 + 그 결과 row 수 (N) 만큼 추가 쿼리.

운영 환경에서 DB CPU 100% 박는 주범 중 하나.

## 2. 발생 조건

- `findAll()` (또는 JPQL) 로 부모 N 개 조회
- 루프 안에서 *LAZY 연관* 접근 → 각 부모마다 별도 쿼리

**EAGER 라도 N+1 발생 가능**:
- `findAll()` 의 JPQL `SELECT b FROM Board b` 는 *Board 만* 가져옴
- Hibernate 가 EAGER 인 연관 (`b.replies`) 을 *나중에 별도 SELECT* → 결국 N+1

EAGER 가 *오히려 N+1 을 숨김*. 그래서 LAZY 권장.

## 3. 해결책 4 가지

### A. JPQL `JOIN FETCH` — 가장 흔함

```java
@Query("SELECT b FROM Board b LEFT JOIN FETCH b.replies")
List<Board> findAllWithReplies();
```

SQL 한 방:
```sql
SELECT b.*, r.* FROM board b LEFT JOIN reply r ON r.board_id = b.id
```

**제약**:
- `OneToMany` JOIN FETCH 시 **페이징 (Pageable) 동시 사용 금지** (메모리 페이징 fallback)
- `DISTINCT` 또는 `Set<Reply>` 로 *중복 제거* 권장 (LEFT JOIN 결과의 row 부풀림)

### B. `@EntityGraph` — Repository 메서드에 부착

```java
@EntityGraph(attributePaths = "replies")
List<Board> findAll();
```

JPQL 안 쓰고 메서드 이름 규칙·기본 메서드에 적용 가능. 내부적으로 JOIN FETCH 와 동등.

```java
@EntityGraph(attributePaths = {"replies", "category"})
@Query("SELECT b FROM Board b WHERE b.viewCnt > :min")
List<Board> popular(@Param("min") int min);
```

### C. `@BatchSize` — 한 번에 IN 절로

```java
@OneToMany(mappedBy = "board")
@BatchSize(size = 100)
private List<Reply> replies;
```

`findAll()` + 루프 시:
- 첫 게시글의 `getReplies()` 호출 시점에 **다음 99 개 게시글의 댓글도 미리 IN 절로 가져옴**
- 1 + ceil(N/100) 쿼리 (1000 개 게시글 → 11 쿼리)

JOIN FETCH 와 달리 **페이징과 함께 사용 가능**.

전역 설정:
```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

### D. DTO Projection — 컬렉션 따로 가져오기

```java
@Query("SELECT new com.example.dto.BoardSummary(b.id, b.title) FROM Board b WHERE ...")
List<BoardSummary> findSummaries(...);
```

부모만 DTO 로. 자식이 필요하면 *별도 쿼리* + IN 절로 묶기.

대규모·페이징 시 가장 안전.

## 4. 해결책 선택 가이드

| 상황 | 추천 |
|--|--|
| 단순 단건 부모 + 자식 컬렉션 | **JOIN FETCH** |
| 페이징 필요 + 자식 컬렉션 | **DTO Projection** 또는 **@BatchSize** |
| 여러 곳에서 같은 fetch | **@EntityGraph** |
| 전역 default | `default_batch_fetch_size = 100` |

# Part G. cascade 와 orphanRemoval

## 1. cascade — 부모 작업의 자식 전파

```java
@OneToMany(mappedBy = "board", cascade = CascadeType.ALL)
private List<Reply> replies;
```

CascadeType:

| 타입 | 동작 |
|--|--|
| `PERSIST` | 부모 `persist` 시 자식도 `persist` |
| `MERGE` | 부모 `merge` 시 자식도 `merge` |
| `REMOVE` | 부모 `remove` 시 자식도 `remove` |
| `REFRESH` | 부모 `refresh` 시 자식도 |
| `DETACH` | 부모 `detach` 시 자식도 |
| `ALL` | 위 모두 |

## 2. 사용 예

```java
@Transactional
public void createWithReplies() {
    Board b = new Board();
    b.setTitle("Hello");

    Reply r1 = new Reply();
    r1.setContent("first");
    r1.setBoard(b);
    b.getReplies().add(r1);

    boardRepo.save(b);   // cascade = ALL 덕분에 r1 도 자동 INSERT
}
```

cascade 없으면 r1 도 별도로 `replyRepo.save(r1)` 해야 함.

## 3. orphanRemoval — 컬렉션에서 제거된 자식 자동 DELETE

```java
@OneToMany(mappedBy = "board",
           cascade = CascadeType.ALL,
           orphanRemoval = true)
private List<Reply> replies;
```

```java
@Transactional
public void removeReply(Long boardId, Long replyId) {
    Board b = boardRepo.findById(boardId).orElseThrow();
    b.getReplies().removeIf(r -> r.getId().equals(replyId));
    // 트랜잭션 commit 시:
    // DELETE FROM reply WHERE id = replyId
}
```

`orphanRemoval = false` 면 `Reply.board` 가 null 이 되거나 미상. 보통은 `true`.

## 4. cascade 사용 시 주의

- **`CascadeType.REMOVE` 또는 `orphanRemoval = true` 는 *해당 자식이 부모에 독점적으로 묶일 때만* 안전**.
- 자식이 *여러 부모* 를 가질 수 있으면 (다른 객체에서도 참조) 위험.
- DDD 의 *Aggregate Root* 패턴에 자연스럽게 부합 (부모가 자식의 lifecycle 을 소유).

# Part H. `@OneToOne` 과 `@ManyToMany`

## 1. `@OneToOne`

```java
@Entity
public class Member {
    @Id @GeneratedValue
    private Long id;

    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "profile_id")
    private Profile profile;
}

@Entity
public class Profile {
    @Id @GeneratedValue
    private Long id;

    @OneToOne(mappedBy = "profile", fetch = FetchType.LAZY)
    private Member member;
}
```

- 디폴트 EAGER → **반드시 LAZY 명시**
- FK 를 *어느 쪽에* 둘지 선택. 보통 *자주 조회되는* 쪽에.
- 양방향 시 `mappedBy` 로 주인 명시 (FK 가 있는 쪽이 주인).

> **함정**: `@OneToOne` 의 *반대편* (`mappedBy` 쪽) 은 *LAZY 가 안 됨* (Hibernate 의 구현 한계). 강제로 LAZY 명시해도 *부모 조회 시 별도 SELECT 발행*. 회피하려면 `@OneToOne` 단방향 만 사용.

## 2. `@ManyToMany` — 거의 사용 X

```java
// 비추
@Entity
public class Student {
    @ManyToMany
    @JoinTable(name = "student_course",
               joinColumns = @JoinColumn(name = "student_id"),
               inverseJoinColumns = @JoinColumn(name = "course_id"))
    private List<Course> courses;
}
```

문제:
- 중간 테이블 (`student_course`) 에 *추가 컬럼* (수강일·성적 등) 을 추가하기 어려움
- 어떤 SQL 이 발행되는지 추적 어려움
- cascade·orphanRemoval 의도와 어긋남

**권장 — 중간 엔티티로 풀기**:

```java
@Entity
public class Enrollment {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "student_id")
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "course_id")
    private Course course;

    private LocalDateTime enrolledAt;
    private Integer score;   // 추가 정보 자유롭게
}
```

`@ManyToMany` 두 개를 `@OneToMany(Enrollment)` + `@ManyToOne` 두 개로 풀어쓰는 것. **항상 이 패턴**.

---

# Part I. 양방향 편의 메서드 패턴

## 1. 문제

```java
@Transactional
public void addReply(Long boardId, String content) {
    Board b = boardRepo.findById(boardId).orElseThrow();
    Reply r = new Reply();
    r.setContent(content);
    r.setBoard(b);                   // 주인 쪽 세팅 (FK 결정)
    // b.getReplies().add(r);         // ← 깜박하면 객체 그래프 불일치
}
```

`r.setBoard(b)` 만 하면 DB 는 정상 (FK 채워짐) 이지만 *메모리의 `b.replies`* 에는 r 이 없음. 같은 트랜잭션에서 `b.getReplies()` 접근 시 **r 이 빠진 옛 컬렉션** 보일 수 있음.

## 2. 해결 — 편의 메서드

```java
@Entity
public class Board {
    @OneToMany(mappedBy = "board", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Reply> replies = new ArrayList<>();

    // 편의 메서드 - 양쪽 동시 세팅
    public void addReply(Reply r) {
        replies.add(r);
        r.setBoard(this);
    }
}
```

```java
b.addReply(r);   // 깔끔
```

## 3. 양방향에서 setter 가리기

더 엄격한 패턴:

```java
@Entity
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class Reply {

    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "board_id")
    @Setter(AccessLevel.NONE)   // 외부에서 reply.setBoard(b) 금지
    private Board board;

    // 패키지 protected - Board.addReply 에서만 호출
    void changeBoard(Board b) { this.board = b; }
}
```

도메인 일관성 보장. 단, 보일러 늘어남.

## 자주 빠지는 함정

| 함정 | 해결 |
|--|--|
| `@ManyToOne` 디폴트가 EAGER 라는 사실 모름 | **항상 `fetch = FetchType.LAZY` 명시** |
| `@OneToOne` 도 디폴트 EAGER | 동일하게 LAZY 명시 |
| `@OneToMany` 만 단방향 매핑 (mappedBy 없이) | 별도 UPDATE 쿼리 발생. `@ManyToOne` 을 주인으로 두기 |
| `mappedBy` 와 `@JoinColumn` 을 *같은 쪽에* 동시 사용 | 둘 중 하나만. `mappedBy` 는 *주인 아님* 선언, `@JoinColumn` 은 *주인* 선언 |
| N+1 문제를 *EAGER 로 해결* 시도 | EAGER 가 *오히려 N+1 을 숨김*. LAZY + JOIN FETCH/EntityGraph/BatchSize |
| **JOIN FETCH + `OneToMany` + 페이징** 동시 사용 | 메모리 페이징 fallback → OOM. DTO Projection 또는 두 쿼리 분리 |
| JOIN FETCH 결과의 *row 부풀림* | `SELECT DISTINCT` 또는 `Set<Reply>` 사용 |
| `@ManyToMany` 직접 사용 | 중간 엔티티 + `@ManyToOne` 두 개로 풀기 |
| 양방향 편의 메서드 없이 한쪽만 set | 객체 그래프 불일치. 편의 메서드 패턴 사용 |
| cascade=ALL + orphanRemoval=true 를 *공유 자식* 에 적용 | 다른 곳에서 참조되면 위험. *독점 소유* 일 때만 |
| `@OneToOne` 의 *반대편 (mappedBy)* 이 LAZY 안 됨 | Hibernate 구현 한계. 단방향만 쓰거나 `@MapsId` 활용 |
| LAZY 컬렉션을 Controller 에서 직렬화 → `LazyInitializationException` (OSIV=false 시) | 2 강의 OSIV / DTO 변환 |
| 양방향 + Lombok `@ToString` | 무한 순회 StackOverflowError. `@ToString.Exclude` 또는 `@Data` 자체를 안 쓰기 |
| `@OneToMany` 의 `List<T>` 가 *순서 의미* | DB 에서 INSERT 순서 보장 X. 순서 필요하면 `@OrderBy` 또는 `@OrderColumn` |

## 자가점검

1. 객체와 RDB 의 *연관관계 표현 차이* 를 한 줄로.
2. **연관관계의 주인** 이란 무엇이고, 어떻게 정하는지.
3. `mappedBy` 가 있는 쪽의 변경이 DB 에 반영되지 않는 이유.
4. `@ManyToOne`, `@OneToOne`, `@OneToMany`, `@ManyToMany` 의 *디폴트 fetch* 를 각각 적으시오.
5. **N+1** 문제가 *발생하는 조건* 과 *해결책 4 가지*.
6. JOIN FETCH 와 페이징을 함께 *쓰면 안 되는* 이유.
7. `@BatchSize` 가 JOIN FETCH 보다 *좋은 경우* 는?
8. `cascade = REMOVE` 와 `orphanRemoval = true` 의 *차이*.
9. `@ManyToMany` 대신 *중간 엔티티* 를 권장하는 이유 두 가지.
10. 양방향 편의 메서드가 *왜 필요한가*. 없으면 무엇이 깨지나?
11. `@OneToOne` 의 반대편이 *LAZY 가 잘 안 되는* 이유.
12. DDD 의 *Aggregate* 패턴이 JPA 의 `cascade` 와 어떻게 어울리는지.

<details><summary>풀이</summary>

1. **객체는 양방향 참조**, **테이블은 한 방향 FK**. 이 비대칭을 *주인* 개념으로 흡수.
2. **FK 컬럼을 결정·관리** 하는 쪽. 보통 `@ManyToOne` (FK 가 있는 쪽). 반대편은 `mappedBy` 로 *주인 아님* 선언.
3. JPA 는 *주인 쪽의 필드* 만 보고 SQL 발행. `mappedBy` 쪽은 *읽기 전용 거울*. 양방향 일관성은 *편의 메서드* 로 코드에서 챙겨야.
4. `@ManyToOne`: **EAGER** (함정). `@OneToOne`: **EAGER** (함정). `@OneToMany`: LAZY. `@ManyToMany`: LAZY. 그러나 *모두 LAZY 명시 권장*.
5. **조건**: 부모 N 개 조회 후 루프에서 LAZY 연관 접근. **해결**: ① JOIN FETCH, ② @EntityGraph, ③ @BatchSize, ④ DTO Projection.
6. `OneToMany` JOIN FETCH 는 row 가 *부풀어짐* (게시글 1개 + 댓글 N 개 = N row). DB 의 `LIMIT/OFFSET` 으로 row 단위 자르면 *게시글이 완전 로딩 안 됨*. Hibernate 는 *메모리 페이징 fallback* → OOM 위험.
7. **페이징과 함께 사용해야 할 때**, 또는 *여러 연관* 을 동시에 가져와도 row 가 부풀지 않아야 할 때. JOIN FETCH 는 한 컬렉션만, @BatchSize 는 IN 절로 묶어 *별도 쿼리* 발행.
8. `cascade = REMOVE`: 부모 `remove()` 시 자식도 `remove()`. **부모 자체가 사라질 때만**. `orphanRemoval = true`: 부모의 *컬렉션에서 자식이 제거되면* 자식 DELETE. **자식이 컬렉션에서 빠지면**. 둘 다 동시에 쓸 수 있음.
9. ① **중간 테이블에 추가 컬럼** (수강일·성적·메타) 추가 가능. ② **명시적 엔티티** 라 cascade·조회 SQL 추적 쉬움. (보너스: `@ManyToMany` 의 발행 SQL 이 의도와 어긋나는 경우가 많음.)
10. 한쪽만 set 하면 *메모리의 부모 컬렉션* 또는 *자식 참조* 가 옛 값 유지 → 같은 트랜잭션에서 그 컬렉션·참조 접근 시 *불일치 보임*. DB 는 주인 쪽 변경만 반영되므로 정상. 메모리 객체 그래프 일관성을 위해 편의 메서드 필요.
11. Hibernate 가 LAZY 프록시를 만들려면 *FK 가 있는 쪽* 이 필요. 반대편 (`mappedBy`) 은 *FK 가 없어* 프록시 생성 어려움 — 부모 조회 시 *연관 객체의 존재 여부* 를 확인해야 하므로 **별도 SELECT 가 발행**. 단방향만 쓰거나 `@MapsId` (PK 공유) 로 회피.
12. **Aggregate Root** = 자식의 lifecycle 을 *소유* 하는 부모. `cascade = ALL + orphanRemoval = true` 가 그 모델 그대로. Aggregate 외부에서는 *Aggregate Root* 를 통해서만 자식에 접근. JPA 의 연관관계 모델이 DDD 와 자연스럽게 부합.

</details>
