> 14문항. 개념·적용·디버그·면접. N=텍스트 길이, M=패턴 길이.

### Q1. (개념) 패턴매칭 4가지 알고리즘의 시간 복잡도 비교?

<details><summary>정답</summary>

| 알고리즘 | 평균 | 최악 | 전처리 | 특징 |
|--|--|--|--|--|
| **단순 비교** | O(N·M) | O(N·M) | 없음 | 짧은 패턴, 작은 텍스트 |
| **KMP** | O(N + M) | O(N + M) | O(M) 실패 함수 | **선형**, 안정적 |
| **Boyer-Moore** | O(N/M) | O(N·M) | O(M + 알파벳) | **영어 grep 최강** |
| **라빈-카프** | O(N + M) | O(N·M) | O(M) | **다중 패턴** 강함 |

**선택 가이드**:
- 단일 패턴 + 일반 텍스트 → **KMP** (worst-case 안정)
- 영문 + 큰 텍스트 (`grep`) → **Boyer-Moore**
- 다중 패턴 동시 검색 → **라빈-카프** 또는 **Aho-Corasick**
- 코딩테스트 일반 → 자바 `String.indexOf` (내부 단순 비교 변형)

**왜 KMP·BM 이 빠른가**: 단순 비교는 텍스트 포인터를 뒤로 되돌리지만, KMP/BM 은 **이미 본 정보를 활용해 점프**.

</details>

### Q2. (개념) KMP 의 "실패 함수 (failure function)" 가 의미하는 바?

<details><summary>정답</summary>

**정의**: `f[i]` = 패턴 `p[0..i]` 의 **접두사와 접미사가 일치하는 최대 길이** (자기 자신 제외).

**예**: 패턴 `"ABABCABAB"`
```
i:   0 1 2 3 4 5 6 7 8
p:   A B A B C A B A B
f:   0 0 1 2 0 1 2 3 4
```

| `i` | `p[0..i]` | 접두사 = 접미사 | `f[i]` |
|--|--|--|--|
| 0 | `A` | (없음) | 0 |
| 1 | `AB` | (없음) | 0 |
| 2 | `ABA` | `A` | 1 |
| 3 | `ABAB` | `AB` | 2 |
| 4 | `ABABC` | (없음) | 0 |
| 5 | `ABABCA` | `A` | 1 |
| 6 | `ABABCAB` | `AB` | 2 |
| 7 | `ABABCABA` | `ABA` | 3 |
| 8 | `ABABCABAB` | `ABAB` | 4 |

**왜 필요한가**: 매칭 실패 시 `j = f[j - 1]` 로 점프 → **텍스트 포인터는 안 움직이고 패턴만 뒤로**.

**효과**: 텍스트 한 번만 훑음 → O(N + M).

</details>

### Q3. (적용) 패턴 `"ABABC"` 의 실패 함수를 직접 계산.

<details><summary>정답</summary>

```
i:   0 1 2 3 4
p:   A B A B C
f:   ?
```

**단계별**:
- `i=0`: `p[0..0] = "A"` → 자기 자신 외 접두사·접미사 없음 → `f[0] = 0`
- `i=1`: `p[0..1] = "AB"` → 일치 없음 → `f[1] = 0`
- `i=2`: `p[0..2] = "ABA"` → "A" 일치 → `f[2] = 1`
- `i=3`: `p[0..3] = "ABAB"` → "AB" 일치 → `f[3] = 2`
- `i=4`: `p[0..4] = "ABABC"` → "C" 끝나니 일치 없음 → `f[4] = 0`

**결과**:
```
i:   0 1 2 3 4
p:   A B A B C
f:   0 0 1 2 0
```

**검증 (KMP 동작)**:
텍스트 `"ABABABC"` 에서 `"ABABC"` 검색:
1. `i=0,j=0` ~ `i=3,j=3` 매칭 (`ABAB`)
2. `i=4,j=4`: `t[4]='A' != p[4]='C'` → 실패
3. `j = f[3] = 2` → `j=2` 로 점프
4. `i=4,j=2`: `t[4]='A' == p[2]='A'` → 매칭, `j=3`
5. 계속 매칭하여 `i=6, j=4` 에서 `j==m` → 매칭 위치 `i-m+1 = 2` 반환

</details>

### Q4. (적용) KMP 알고리즘 자바 구현.

<details><summary>정답</summary>

```java
// 1. 실패 함수 계산
static int[] failure(String p) {
    int m = p.length();
    int[] f = new int[m];
    int k = 0;
    for (int i = 1; i < m; i++) {
        while (k > 0 && p.charAt(k) != p.charAt(i)) {
            k = f[k - 1];        // 더 짧은 접두사로 후퇴
        }
        if (p.charAt(k) == p.charAt(i)) k++;
        f[i] = k;
    }
    return f;
}

// 2. KMP 검색
static int kmp(String t, String p) {
    int[] f = failure(p);
    int n = t.length(), m = p.length(), j = 0;
    for (int i = 0; i < n; i++) {
        while (j > 0 && t.charAt(i) != p.charAt(j)) {
            j = f[j - 1];        // 패턴 점프 (텍스트 포인터는 안 움직임)
        }
        if (t.charAt(i) == p.charAt(j)) j++;
        if (j == m) return i - m + 1;   // 매칭 위치
    }
    return -1;                            // 없음
}
```

**핵심**:
- 텍스트 포인터 `i` 는 **절대 뒤로 안 감** (for 루프 단방향)
- 매칭 실패 시 패턴 포인터 `j` 만 `f[j-1]` 로 점프
- amortized O(N + M)

**모든 매칭 위치 찾기**:
```java
static List<Integer> kmpAll(String t, String p) {
    int[] f = failure(p);
    int n = t.length(), m = p.length(), j = 0;
    List<Integer> hits = new ArrayList<>();
    for (int i = 0; i < n; i++) {
        while (j > 0 && t.charAt(i) != p.charAt(j)) j = f[j - 1];
        if (t.charAt(i) == p.charAt(j)) j++;
        if (j == m) {
            hits.add(i - m + 1);
            j = f[j - 1];     // 다음 매칭 위해 점프
        }
    }
    return hits;
}
```

</details>

### Q5. (개념) Boyer-Moore 의 두 가지 휴리스틱 (bad character / good suffix)?

<details><summary>정답</summary>

**Boyer-Moore 특징**: 패턴을 **뒤에서부터 비교**. 안 맞으면 큰 폭으로 점프.

**1. Bad Character (나쁜 글자) 휴리스틱**:
- 텍스트의 안 맞은 글자가 **패턴에 없으면** → 패턴 전체 길이만큼 점프
- 패턴 안에 있으면 → 가장 오른쪽 위치만큼 점프

```
텍스트: ABCXABCDE
패턴:   ABCDE
        ^^^^^
                 비교 시작 (뒤에서 D 와 X 비교)
        text[3]='X' != pat[3]='D'
        X 가 패턴에 없음 -> 패턴 길이(5)만큼 점프
```

**2. Good Suffix (좋은 접미사) 휴리스틱**:
- 매칭된 접미사가 패턴 안에서 다시 나타나는 위치로 점프
- 또는 매칭된 접미사의 접두사와 일치하는 패턴 접두사로

```
패턴: ABCABC
끝의 "ABC" 매칭됨 -> 패턴 앞쪽 "ABC" 와 정렬
```

**둘 다 사용** - 더 큰 점프 선택.

**Bad character 만의 단순 구현 (충분히 빠름)**:
```java
static int[] badCharTable(String p) {
    int[] table = new int[256];   // 알파벳 크기
    Arrays.fill(table, -1);
    for (int i = 0; i < p.length(); i++) {
        table[p.charAt(i)] = i;   // 가장 오른쪽 위치
    }
    return table;
}
```

</details>

### Q6. (디버그) Boyer-Moore 가 영어에 강하고 한글에 약한 이유?

<details><summary>정답</summary>

**핵심**: Bad Character 휴리스틱은 **알파벳 크기** 에 효과가 좌우.

**영어 (알파벳 26자)**:
- 패턴에 안 들어가는 글자 확률 ↑ → 큰 점프 자주
- 평균 O(N/M) 의 성능

**한글 (수만 자)**:
- 패턴에 안 들어가는 글자 확률은 같지만, **각 글자가 등장 빈도 낮음**
- 한글 텍스트는 각 글자가 매우 다양 → 패턴 안에 있을 확률도 낮지만, 점프 폭이 보통 1~3 정도로 작음
- BM 의 최대 강점이 약화

**해결책**:
- 한글에는 **KMP** 가 더 안정적 (알파벳 크기 영향 없음)
- 또는 **UTF-8 바이트 단위** 로 BM 적용 (256자 → BM 효과 유지)

**문자 인코딩 함정**:
```java
// 한글 char (16-bit) - bad char 테이블 65536 크기
int[] table = new int[65536];

// 또는 byte 단위
byte[] textBytes = text.getBytes(StandardCharsets.UTF_8);
byte[] patBytes = pattern.getBytes(StandardCharsets.UTF_8);
// bad char 테이블 256 크기
```

**일반 원칙**: 알고리즘 선택 시 **알파벳 크기 (Σ)** 도 고려.

</details>

### Q7. (개념) 라빈-카프의 Rolling Hash 원리.

<details><summary>정답</summary>

**아이디어**: 패턴과 텍스트 윈도우를 해시값으로 비교. 해시는 O(1) 갱신.

**Rolling Hash 수식**:
```
h(t[0..k]) = t[0] * base^k + t[1] * base^(k-1) + ... + t[k]

h(t[1..k+1]) = (h(t[0..k]) - t[0] * base^k) * base + t[k+1]
```

**예** (base=256):
- 텍스트 `"AB"` → `'A'*256 + 'B' = 65*256 + 66 = 16706`
- 윈도우 한 칸 이동 (`"BC"`) → `(16706 - 65*256) * 256 + 67 = 66 * 256 + 67 = 16963`

**자바 구현 (mod 사용)**:
```java
static List<Integer> rabinKarp(String t, String p) {
    int n = t.length(), m = p.length();
    int base = 256, mod = 1_000_000_007;

    long ph = 0, th = 0, pow = 1;
    // 초기 해시 + base^(m-1) 계산
    for (int i = 0; i < m; i++) {
        ph = (ph * base + p.charAt(i)) % mod;
        th = (th * base + t.charAt(i)) % mod;
        if (i < m - 1) pow = (pow * base) % mod;
    }

    List<Integer> hits = new ArrayList<>();
    for (int i = 0; i <= n - m; i++) {
        // 해시 일치 + 실제 문자열도 일치 (충돌 검증)
        if (ph == th && t.regionMatches(i, p, 0, m)) {
            hits.add(i);
        }
        // Rolling: 다음 윈도우로 이동
        if (i < n - m) {
            th = (th - t.charAt(i) * pow % mod + (long) mod * mod) % mod;
            th = (th * base + t.charAt(i + m)) % mod;
        }
    }
    return hits;
}
```

**시간 복잡도**:
- 초기 해시: O(M)
- Rolling: 각 칸 O(1) → 총 O(N)
- 합계 O(N + M)

**다중 패턴 강점**: 패턴이 여러 개면 **모두 같은 해시 계산식** → 텍스트 해시 한 번만 계산하고 여러 패턴과 비교.

</details>

### Q8. (디버그) 라빈-카프에서 해시값이 같아도 실제 문자열 비교가 필요한 이유?

<details><summary>정답</summary>

**이유**: **해시 충돌 (Hash Collision)** - 다른 두 문자열이 같은 해시값을 가질 수 있음.

**왜 충돌이 불가피한가**:
- 해시는 무한한 입력 (모든 가능한 문자열) 을 유한한 출력 (예: 64-bit 정수) 으로 매핑
- 비둘기집 원리 (Pigeonhole Principle) - 어쩔 수 없이 충돌

**예** (base=256, mod=11):
- `"AB"` → `(65*256 + 66) % 11 = 16706 % 11 = 5`
- `"BC"` → `(66*256 + 67) % 11 = 16963 % 11 = 5` (충돌 가능)

→ 해시만으로 같다고 하면 잘못된 매칭.

**올바른 패턴**:
```java
if (ph == th) {
    // 1차 필터 통과 - 실제 문자열 비교 (확실)
    if (t.regionMatches(i, p, 0, m)) {
        hits.add(i);
    }
}
```

**비용 분석**:
- 해시 비교: O(1) - 매번
- 실제 비교: O(M) - 해시 일치 시에만
- 충돌이 적으면 → 거의 모든 위치 O(1) → 전체 O(N + M)
- 충돌이 많으면 (안 좋은 해시 함수) → 매번 O(M) → O(N·M) 최악

**좋은 해시 함수의 조건**:
- 충돌 확률 균등 분포
- 큰 prime modulus 사용 (`1_000_000_007`, `998_244_353`)
- Double Hashing (두 다른 해시 함수 동시 확인) - 충돌 확률 제곱으로 감소

**암호화 해시 (SHA-256) 도 이론적 충돌 가능** - 단지 발견하기 매우 어려움.

</details>

### Q9. (디버그) 단순 비교가 최악 O(N·M) 이 되는 입력 예와 분석?

<details><summary>정답</summary>

**최악 입력**:
```
텍스트: "AAAAAAAAAAB"  (A 가 많고 끝에 B)
패턴:   "AAAAB"        (A 가 많고 끝에 B)
```

**동작**:
- 위치 0: AAAA 까지 매칭 (4번 비교) → A vs B 실패
- 위치 1: AAAA 까지 매칭 (4번) → 실패
- 위치 2: 같음
- ...
- 위치 6: AAAAB 매칭 성공!

**비교 횟수**: 각 위치마다 M 번 비교 → 총 (N - M + 1) x M ≈ N·M

**분석**: 단순 비교가 텍스트 포인터를 **매번 뒤로 되돌림**.
```java
for (int i = 0; i <= n - m; i++) {       // N 번
    int j = 0;
    while (j < m && t.charAt(i+j) == p.charAt(j)) j++;   // M 번
}
```

**해결 - KMP**:
- 위치 0: AAAA 까지 매칭 → A vs B 실패
- `j = f[3] = 3` (3 글자 일치 = 다음 위치에서 3 글자 매칭 효과)
- 텍스트 포인터 `i` 안 움직이고 패턴만 점프
- → 총 비교 횟수 O(N + M)

**실무**: 1MB 텍스트 + 100 글자 패턴 = 100MB 비교 vs 1MB 비교 (100배 차이).

**자바 String.indexOf 도 단순 비교 변형**:
- 작은 입력엔 충분
- TLE 나는 코딩테스트는 KMP 직접 구현

</details>

### Q10. (적용) 여러 패턴을 동시에 검색하려면? (Aho-Corasick)

<details><summary>정답</summary>

**문제**: 백신 시그니처 1000개를 1GB 파일에서 검색.
- KMP 1000번 반복 → O(1000 x (N + M)) = O(1000N)
- 더 빠른 방법 = **Aho-Corasick**

**Aho-Corasick 핵심**:
1. 모든 패턴을 **트라이 (Trie)** 로 합침
2. KMP 의 실패 함수를 트라이로 일반화 (failure link)
3. 텍스트를 **한 번만** 훑으며 모든 패턴 동시 검색

```
패턴: "he", "she", "his", "hers"

트라이:
        root
       / |  \
      h  s   (다른 시작)
     /|  \
    e i   h
    | |   |
    [he] [his] e
              |
              [she]

실패 링크: 매칭 실패 시 다른 패턴 노드로 점프
```

**시간 복잡도**:
- 트라이 구축: O(sum of pattern lengths)
- 검색: O(N + occurrences)
- → **모든 패턴 합쳐서 한 번만**

**자바 구현 골격**:
```java
class AhoCorasick {
    Node root = new Node();

    void addPattern(String p) {
        Node cur = root;
        for (char c : p.toCharArray()) {
            cur = cur.children.computeIfAbsent(c, k -> new Node());
        }
        cur.outputs.add(p);
    }

    void build() { /* BFS 로 failure link 구축 */ }

    List<Match> search(String text) { /* 텍스트 훑으며 매칭 */ }
}
```

**실무 사용**:
- 백신 (시그니처 매칭)
- `grep -F -f patterns.txt` (다중 패턴 fixed-string grep)
- DPI (Deep Packet Inspection)
- 검색 엔진 키워드 매칭

</details>

### Q11. (개념) 자바 `String.indexOf` 의 내부 알고리즘과 한계?

<details><summary>정답</summary>

**JDK 구현** (`java.lang.String#indexOf`):
- 기본은 **단순 비교 변형** (작은 패턴 최적화)
- 일부 휴리스틱 (첫 글자 빠른 검색)
- 일부 JVM 은 SIMD 가속

```java
"hello world".indexOf("world");        // 6
"hello world".indexOf("xyz");          // -1
"hello world".contains("world");       // true (내부적으로 indexOf)
```

**시간 복잡도**: 평균 O(N + M), 최악 O(N·M).

**언제 충분?**:
- 일반 텍스트 처리 (대부분의 경우)
- 짧은 패턴, 작은 텍스트
- 코딩테스트의 단순 검색

**언제 안 충분?**:
- 1MB+ 텍스트 + 긴 패턴 (KMP 필요)
- 다중 패턴 (Aho-Corasick)
- 최악 케이스 보장 필요 (보안, SLA)

**Java 정규식 (`Pattern`)**:
```java
Pattern p = Pattern.compile("\\d+");
Matcher m = p.matcher("abc 123 def 456");
while (m.find()) {
    System.out.println(m.group());     // "123", "456"
}
```
- 내부: NFA → DFA 또는 backtracking
- 단순 고정 패턴은 KMP/BM 이 더 빠름
- 백트래킹 정규식은 **catastrophic backtracking** 위험 (`(a+)+b` + 긴 `aaaa...`)

**코딩테스트 가이드**:
1. 첫 시도: `String.indexOf`
2. TLE 발생: KMP 직접 구현
3. 다중 패턴: Aho-Corasick 또는 라빈-카프

</details>

### Q12. (개념) 정규식 vs KMP/Boyer-Moore - 언제 무엇을?

<details><summary>정답</summary>

| | 정규식 | KMP/BM |
|--|--|--|
| **표현력** | 매우 높음 (메타문자, 그룹, 백참조) | 고정 패턴만 |
| **속도 (단순 패턴)** | 보통 | **빠름** |
| **속도 (복잡 패턴)** | 일반화 가능 | X (특정 도구만) |
| **컴파일 비용** | NFA->DFA 변환 (느림) | O(M) 실패 함수 |
| **최악 보장** | 백트래킹 시 X | 항상 선형 |

**정규식이 좋은 경우**:
- 패턴이 동적 (사용자 입력 정규식)
- 메타문자 필요 (`\d`, `\s`, `.*`, `[A-Z]+`)
- 캡처 그룹 (`(\d+)-(\d+)`)
- 코드 가독성 (한 줄로 표현)

```java
// 정규식 - 이메일 검증
boolean valid = email.matches("[\\w.]+@[\\w.]+\\.[a-z]{2,}");

// 정규식 - 추출
Matcher m = Pattern.compile("(\\d+)-(\\d+)").matcher("range 10-20");
if (m.find()) {
    int from = Integer.parseInt(m.group(1));
    int to = Integer.parseInt(m.group(2));
}
```

**KMP/BM 이 좋은 경우**:
- 고정 패턴 (변하지 않음)
- 거대한 텍스트 (1GB+)
- 최악 케이스 보장 필요
- grep 같은 도구의 내부

**Catastrophic Backtracking 함정**:
```java
// 안 좋은 예 - O(2^n) 가능
Pattern.compile("(a+)+b").matcher("aaaaaaaaaaaaaa!").matches();
// 거의 무한 루프 (ReDoS 공격 벡터)

// 좋은 예
Pattern.compile("a+b").matcher("aaaaaaaaaaaaaa!").matches();
// O(N)
```

**RE2 라이브러리** (Google): 백트래킹 없는 정규식 엔진 (linear time guarantee).

→ Java 표준 정규식은 백트래킹 기반이라 ReDoS 위험. 사용자 입력 정규식은 신뢰 X.

</details>

### Q13. (개념) 스트리밍 / 대용량 파일 처리에 적합한 알고리즘 = "백트래킹 없음" 의 의미?

<details><summary>정답</summary>

**스트리밍 처리**: 데이터가 한 번 흘러가면 다시 볼 수 없음 (네트워크 패킷, 대용량 파일 cat).

**조건**:
- 텍스트 포인터가 **앞으로만** 진행
- 한 번 본 위치로 **되돌아갈 필요 없음** (random access 불필요)

**적합한 알고리즘**:

| 알고리즘 | 스트리밍 OK? | 이유 |
|--|--|--|
| **KMP** | O | 텍스트 포인터 단방향 |
| **Aho-Corasick** | O | 다중 패턴도 단방향 |
| **Boyer-Moore** | X | 뒤에서 비교 → random access 필요 |
| **라빈-카프** | 부분 OK | 윈도우 단방향이지만 메모리에 m 글자 유지 |
| **단순 비교** | X | 매번 i 위치로 되돌아감 |

**실무 예 - 로그 스트리밍**:
```java
// 1TB 로그 파일에서 에러 패턴 실시간 검색
try (BufferedReader br = new BufferedReader(new FileReader("huge.log"))) {
    KmpStreamMatcher matcher = new KmpStreamMatcher("ERROR");
    int c;
    while ((c = br.read()) != -1) {
        if (matcher.feed((char) c)) {
            // 매치 발견
            System.out.println("found at offset");
        }
    }
}
```

**Boyer-Moore 가 안 되는 이유**:
- 패턴 끝부터 비교 → 텍스트의 윈도우 끝을 먼저 봄
- 매번 패턴 길이만큼의 **윈도우를 들고 있어야** 함
- 스트리밍에선 한 글자씩 들어옴 → m 글자 모일 때까지 대기 + 메모리 보관 필요

**라빈-카프 (조건부 OK)**:
- 윈도우 m 글자만 메모리 유지하면 OK
- Rolling hash 로 갱신 가능

**네트워크 보안**:
- IDS (Intrusion Detection System) 는 패킷 스트림에 시그니처 매칭
- **Aho-Corasick** 이 표준 (Snort, Suricata)

</details>

### Q14. (면접) "실무에서 패턴매칭 알고리즘이 어디 쓰이나?"

<details><summary>정답</summary>

**1. 텍스트 검색 도구**:
- `grep`, `ripgrep` - 파일에서 패턴 검색 (BM, KMP 사용)
- IDE 의 "Find in Files" (IntelliJ, VS Code)
- 데이터베이스 LIKE / FULLTEXT 검색

**2. 정규식 엔진**:
- 자바 `Pattern`, 파이썬 `re`, JavaScript `RegExp`
- 로그 파싱, 데이터 추출, 검증

**3. 보안 분야**:
- **백신 시그니처 매칭** - Aho-Corasick (수천 개 패턴 동시)
- **IDS/IPS** - 네트워크 패킷의 공격 시그니처 탐지
- **WAF** - 웹 방화벽의 SQL Injection / XSS 패턴

**4. 검색 엔진**:
- 색인 구축 시 토큰화
- 키워드 자동완성 (Trie + 패턴 매칭)
- 광고 매칭 (사용자 검색어 ↔ 광고주 키워드)

**5. 생물정보학**:
- DNA 시퀀스 매칭 (BLAST, BWA)
- 단백질 구조 비교
- Suffix Array / Suffix Tree 활용

**6. 데이터 처리**:
- 로그 분석 (ELK Stack 의 패턴 매칭)
- ETL 파이프라인 (정제 규칙)
- 데이터 마이그레이션 (변환 규칙)

**7. 개발 도구**:
- 컴파일러의 lexer (토큰 인식)
- linter (안티패턴 탐지)
- diff 도구의 LCS (Longest Common Subsequence)

**8. 컴파일러·인터프리터**:
- Syntax Highlighting (에디터의 키워드 색칠)
- Auto-completion (메서드 이름 매칭)

**알고리즘 선택 가이드 (실무)**:

| 시나리오 | 선택 |
|--|--|
| 작은 텍스트 (< 1MB) | `String.indexOf` |
| 큰 영문 텍스트 | Boyer-Moore (grep) |
| 일반 텍스트 안정성 | KMP |
| 1000+ 패턴 | Aho-Corasick |
| 정규식 필요 | 정규식 엔진 (단, ReDoS 주의) |
| DNA 분석 | Suffix Array / FM-index |

**면접 포인트**:
- "어떤 알고리즘을 쓸지" 보다 "왜 그 알고리즘인지" 가 중요
- 입력 크기, 패턴 개수, 메모리 제약, 알파벳 크기 고려
- "코딩테스트에서 KMP 직접 구현 vs 내장 사용" 도 자주 묻는 질문

</details>
